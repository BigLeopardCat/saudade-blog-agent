## 0. 一句话结论

**不稳的不是"工具调用"，是"关于工具调用的话"。**

20260921 那 8 个洞，逐个归类后**没有一个**是"工具没被调用成功"：

| # | 洞 | 层 | 一句话 |
|---|----|----|--------|
| ① | 5c 具名声称闸的兜底文案断言"这一轮没有任何工具执行" | 判定层 | 该闸只在**真有执行**的轮才可能命中（`_phantom_tool_claim_span` 在 `not executed` 时直接返回 None）⇒ 兜底文案 **100% 与回执矛盾**（165645：`create_tag` 真建了「大笨狗」id=15，回复被换成"什么都没执行"） |
| ② | 判据否掉的是哪一句，trace 里没有 | 观测层 | 每次争论判据准不准只能凭手感；误杀/漏判都无法从 trace 复盘 |
| ③ | `list_tags` 只读 `/tagone` | **数据层** | 二级标签在结构上就看不见 ⇒ 答"站内没有二级标签"（不是模型编的，是喂给它的数据如此） |
| ④ | `SITE_GUIDE` 是手写死清单，不含管理能力 | **注入层** | 管理员问"你能做什么"照单答"我不能改后台"（165525/165544 vs 165645/165937：同一能力三轮两种答案，**两句都"有据"**，据的是那份不会动的清单） |
| ⑤ | 5c 把工具返回文本里的工具名当 narrator 自称 | 判定层 | 工具返回文本自带 `set_article_tags`，narrator 照抄 ⇒ 整轮被否（真建成的标签被讲成没建） |
| ⑥ | Rust 把回执顶层 `tag_name` 读成工具实参 | **跨语言契约层** | 每次新建标签都渲染成「新建一级标签「」」（名字恒空），跨轮执行记忆跟着失真 |
| ⑦ | planner 把父标签名当成新标签名（参数对调） | 参数层 | 「在 X 下新建 Y」→ `title=X, parent_id=X的id` |
| ⑧ | 确认弹窗问句缺父标签名 | 交互层 | 只写「新建二级标签「Rust」」⇒ 用户盲签，"挂错父标签"看不出来 |

**8 个里 3 个（③④⑥）是系统自己喂错数据/读错字段，3 个（①⑤⑧）是"描述已发生事实"的环节失真，
2 个（⑦+②）是参数与复盘。** 没有一个是执行器把工具跑飞了——planner 全权 + 确定性 execute +
checker 验收这条主干是稳的：**今天的工具调用全部按计划完成了**。

所以路线图的主轴不是"让工具调用更稳"（它已经稳），而是
**让"系统说了什么"与"系统做了什么"之间不再有 LLM 的自由发挥空间**。

Coding agent 的稳定，恰恰来自它**没有**这个空间：它"改了文件"这件事由文件系统作证，
它对用户说的话就是工具回执本身。本项目现在多了一层——narrator 拿着回执**重新生成**一段话，
再拿 8 族正则去抓这段话有没有撒谎。打得准是运气，打不准是必然。

## 1. Coding agent 的稳定来自哪五条结构性质

（按"对本项目的可移植性"排序；不是模型能力差异——本项目的 planner/narrator 也是同一个量级的模型）

**P1 动作有环境回执，"成功"由环境定义。**
`Edit` 失败会报错、`Bash` 有 exit code、`Read` 之后才知道文件内容。模型**结构上不可能**
"以为"自己改成功了——它没有产出一个"成功"字样的机会，成功是环境的属性。
→ 本项目对照：**写工具已有**（`create_tag` 建后读回复核 `tools/base.py:1029`、
`set_article_status` 读回比对新值 `1104`/`1113`、文章标签读回 `1217`/`1220`）；
**动作类工具没有**（导航/特效/夜间/屏幕显示的"回执"是命令帧，
前端执行完**没有任何回报**——这是本项目最大的无回执盲区）。

**P2 事实只从环境读，"知道"必须有来源。**
用文件内容就重新读，不用记忆里的版本。上下文里的每一段内容都带来源。
→ 本项目对照：`doc_anchors`（文档指代）、`execution_log` + `digest`（跨轮取值）、
`receipts`（本轮事实）已构成三层来源制；缺口是**动作类没有来源**（P1）与**摘要只有一行**
（`detail varchar(300)`，读侧只取 8 行）。

**P3 参数通道是 schema 化的。**
工具参数是结构化 JSON，参数名/类型/枚举由 schema 约束，模型写不出"散文参数"，
也写不出"这个字段其实是另一个字段的意思"。参数的**语义**由 schema 的描述承担，
而描述与校验是同一份东西。
→ 本项目对照：planner 输出 **7 行文本协议**（`SKILL/PARAMS/TOOLS/NOTE/REPLY`），
参数在 `PARAMS` 的 JSON 里由模型写死，事后靠 `instantiate_plan` 的白名单 + 缺参守卫 +
pydantic 三层手工补网。⑦（参数对调）正是这一层的固有事故类型。

**P4 用户看到的（几乎）就是回执。**
tool_use / tool_result 直接进 transcript，模型对执行结果的"转述"不是必须的环节。
→ 本项目对照：narrator **必须**重新生成用户可见文本（`_EXECUTOR_PROMPT`），
回执只作为它的输入。于是"回执为真、叙述失真"变成一类**结构上必然存在**的偏差，
再用 8 族判据事后围堵。

**P5 失败是数据，不是需要圆过去的事。**
错误原样回到模型，模型据此换策略。没有"兜底文案"把失败包装成一句人设内的道歉。
→ 本项目对照：**这一条已经做对了**——`__ERROR__` 帧 + `blocked` reason 码
（`unknown_tool/args_parse/empty_result/error_frame/cmd_shape` + `ref_*` 族 + `consent_required`
+ `unknown_target`）回灌 planner，rule 5 让它改参重试，二次受阻进 reflector。
这是全仓最接近 coding agent 的一处。

## 2. 逐条对照体检

| 性质 | 本项目现状 | 评价 |
|------|-----------|------|
| P1 环境回执 | 写工具 3/3 有读回复核；动作类 0/5 有回报 | **半有**（写侧是标杆，动作侧是空白） |
| P2 事实有来源 | 三层来源制（锚点/回执/摘要）+ 引用绑定 | **基本有**（缺动作侧；摘要偏薄） |
| P3 schema 化参数 | 文本协议 + 三层事后校验 | **没有**（今天 ⑦ 的直接土壤） |
| P4 回执即呈现 | narrator 全量重写用户可见文本 | **没有**（今天 ①⑤ 的直接土壤） |
| P5 失败是数据 | reason 码 + planner 改参重试 + reflector | **有**（保持，别再往这条加判据） |

外加上层的**判定层**（13 处 fallback / 15 个 reason 码）与**观测层**（trace），
它们是在 P3/P4 缺位的情况下不得不长的东西——**判据密度是缺口的度量，不是成熟度的度量**。

## 3. 六个改造方向

按 **收益/成本比** 排序。每条给：现状（带锚点）→ 目标 → 落地步骤 → 验收判据 → 风险。

### D6（先做，成本最低）判据语料化与冻结纪律

**现状**：`gate_node` 里有 13 处 `_fallback_result` 调用点、15 个 reason 码
（6 张编号闸 5a–5f + 1b 逐字复读 + 命令前缀 + 编造 URL + 零帧注记核验 + `_claim_issue` 的 5 个子判据），
词表随每次事故单调增长；
`tests/test_skills.py` 里散着约 20 条布尔断言锁判据，但**没有一份"真实语料 + 期望判定"的基线**，
所以"这次改判据少抓了几条 / 多抓了几条"永远算不出来。今天补的 clause 落 trace
（`_clip_clause` / `_claim_clause` / `_fallback_result(clause=)`）是这条的前置：**先有句子，才有语料**。

**目标**：判据变成有语料、有基线、**只减不增**的资产。

**步骤**
1. 建 `eval/claim_corpus/<族>.jsonl`：每行 `{"text": 原句, "want": true/false, "src": trace_id, "note": 为什么}`。
   语料来源 = 真实 trace（`logs/agent/traces`，全量复扫脚本已有：`/tmp/rescan_state_claim.py` 的做法收编进仓）。
2. `eval/claim_regress.py`：跑全语料 → 输出**差集**（相对基线新增误杀/新增漏判）+ 退出码。
   基线 `eval/report/claim_baseline.json` 与 golden 基线同族管理。
3. 改任何判据必须附差集；CI 跑（秒级，纯函数）。

**验收判据**：改一次判据，终端能打出"少抓 N 条 / 多抓 M 条"并列出句子；
N/M 不为 0 时必须人工签字（写进 `eval/report/review_*.md` 的复审单格式，已有）。

**KPI（反向指标）**：**真实流量里判据命中数 / 100 轮应当趋近 0**。
它居高不下 = 失真源头没被结构消灭，还在打地鼠；它趋近 0 = D3 在生效。

**风险**：低（纯离线资产）。**唯一纪律**：语料只能从真实 trace 抽，不许自己造句
（自己造的句子必然偏向当前判据）。

### D4 planner 输出 schema 化（结构化输出替代文本协议）

**现状**：`planner_node` 输出 7 行文本协议，`_loads_tolerant` 容忍单引号/尾逗号/围栏；
参数由模型在 `PARAMS` JSON 里写死；`instantiate_plan`（`agent/skills.py`）补三层：
白名单校验 → 缺参守卫（`_norm_pos_int` 等）→ pydantic（工具侧）。

**目标**：每个技能一份 JSON Schema，planner 走**结构化输出**；文本协议降级为日志形态（打算法）。
参数语义（含"这个 id 从哪来"）写在 schema 的描述里，**描述与校验同一份**。

**步骤**
1. ~~POC（必须先做）：验证生产模型（qwen 系，OpenAI 兼容端点）对 `response_format=json_schema`
   或 function calling 的支持度与稳定性——**这是本方向的前置未知量，不验证不动手**。~~
   **20260925 已跑完并全部通过**，见下方「D4 POC 结果」；结论带两个协议设计风险，先读那个再动手。
2. `agent/skill_schema.py`：由 `SKILLS` 注册表派生 schema（`inputs` 已是雏形），
   加 `required` / `enum`（如 `status ∈ {public,private,draft}`、`is_top ∈ {0,1}`）、
   加 id 类参数的来源约束（见 D5）。
3. 迁移期**双轨**：schema 输出 → 归一成现有 `plan` 文本 → 其余链路一行不改
   （这样回滚 = 关一个开关，不需要动 execute/gate/回执）。

**验收判据**：`args_parse` / pydantic `ValidationError` / `unknown_target` 三族受阻
在 golden 全量 + 真实回放里**归零**；⑦ 类参数对调**结构上不可能**（父子同名会撞 enum/来源校验）。

**风险**：中。①模型支持度未知（POC 挡在前面）；②结构化输出会挤掉 planner 的"思考"文本，
而 planner 的低温度短输出正是当前决策质量的来源——需要对比决策质量（golden 通过率）不掉。

### D4 POC 结果（20260925 已跑完，前置未知量清空）

脚本 `eval/d4_structured_output_poc.py`（**只发 LLM 请求**：不碰库、不落 trace、不改进程状态；
要网络与真模型，故**不入 L0、不进夜间**）。原始证据是本地留档
`eval/report/d4_poc_20260925_140938.md`（`eval/report/` 按既有约定不入 git），
重跑一次即得：`.venv/bin/python eval/d4_structured_output_poc.py --trials 5 --thinking`。

**结论：支持度不再是未知量——结构化输出与 function calling 在生产端点上都真实可用，
且判别结果是"真约束解码"，不是"接受了但静默忽略"。** 生产 qwen `qwen3.8-flash`
（阿里云 MaaS compatible-mode），与 planner 完全同参（`temperature=0.2 / max_tokens=400 /
timeout=30 / enable_thinking=False`），每档 5 次：

| 档位 | 结果 | p50 延迟 |
|---|---|---|
| 纯文本写 JSON（**今天的形态**，对照） | JSON 可解析 5/5，**满足 schema 0/5**（模型自裁了形状） | 1.55s |
| `response_format=json_schema` + `strict` | **达标 5/5** | 1.53s |
| 同上 + **对抗提示词**（明令把 integer 写成字符串、action 取 enum 外的值） | **5/5 违不了** ★ | 2.36s |
| `response_format=json_object`（弱档）+ 同一对抗提示词 | 5/5 可解析，**顺着提示词违约** | 0.98s |
| tools + `tool_choice=auto` | 5/5 回 tool_call，`arguments` 是合法 JSON | 0.88s |
| tools + 强制指定函数 | 5/5 必回 tool_call | 1.08s |
| tools + 函数侧 `strict=true` | 5/5（无 400） | 0.80s |
| 意图落不进 enum（"删掉「大笨狗」标签"） | 5/5 输出合法，**但内容是错的**（风险①） | 1.80s |

**"真约束"这条是怎么证明的**（这档探针存在的唯一理由）：提示词明说"count 写成字符串、
action 填「关闭」"，**弱档照着写了**（`count:"1"`、`action:"关闭"`），
**strict 档结构上写不出来**（`count:1`、`action:"off"`）。同提示词、只差一个参数 ⇒
"strict 在真约束解码"是实测而非推断。附带两条也精确生效：`required` 里没有的
`action` 时有时无（不是无脑全填）；`additionalProperties:false` 没被绕过。

**顺带清掉的两个未知量**：① 参数不会被端点拒绝（无 400）；② 思考模式与结构化输出**能共存**
（返回 `reasoning_content` + 合法正文），但**延迟从 1.5s 涨到 p50 6.4s / 最大 28.5s**——
planner 的 `timeout=30` 正好压在那条尾巴上。所以 D4 落地要么继续 thinking 关，
要么**单独调这个时限**，不能想当然"开着思考也行"。

**POC 新暴露的两个风险（都不是支持度问题，是协议设计问题，比支持度更该先想清楚）**：

① **约束解码拿走了"这题我不会"这个选项**。P8 的意图落不进那四个 enum 值，
模型**不能**答"没有对应技能"——它只能挑最近似的（`content_query`），再把自由文本部分
填成看着合理的东西。⇒ schema 必须显式留一条"不匹配/闲聊"的出口；否则 D4 会把今天
**零写 + 如实收尾**（剔空纠偏那条路）的轮次降级成**做错事**，比现状更差。

② **`strict` 约束的是形状，不是真假**。P8 里 `tools:["delete_tag"]` 是个**真实存在的工具名**，
但它不在 `content_query` 的通道白名单里（写工具只能由技能模板展开）。
⇒ 结构化输出**不会**替你挡住"参数填了个站内不该用的东西"——那正是 D5 要管的事。
**D4 与 D5 是配套的**；D4 单独上会让人误以为参数问题已经解决。

### D5 参数绑定完备化（id 类参数不再由模型写字面值）

**现状**：`agent/refs.py` 的 `$<工具>[<序号>].<字段>` 已上线（planner 规则 3b），
但它是**可选写法**；prompt 里仍写着"父标签 id 要从标签清单或本轮工具帧里拿到"这种**纪律**，
而纪律靠模型自觉。⑦ 就是自觉失败的样子（手边没有清单时编一个 id，或者把父名当成子名）。

**目标**：把"带来源的值"变成类型——id 类参数**只能**来自 ①本轮已验证帧 ②引用 ③CAS 语料
（`doc_anchors`）。模型写字面 id 时由 validator 校验**该 id 是否出现在它这一轮真看到过的数据里**。

**步骤**
1. schema（D4）里给 id 类参数标来源：`{"x_source": "frame|ref"}`。
2. `instantiate_plan` 侧把 `_target_evidence`（今天只用于文章写，`graph.py:165`）的思路
   推广到**所有** id 类参数；不在证据里 → 零工具 + 注明原因（planner 去取）。
3. 报错码统一进 `refs.py` 的族（`ref_unknown_tool/ref_unparsed/ref_index_range/ref_path_missing/ref_not_scalar`）。

**验收判据**：golden 新增"planner 写了个不存在的 tag id → 零调用 + 明确错误帧"；
真实回放里 `unknown_target` 族归零。

**风险**：低-中。可能误伤"用户原话里就带着 id"的场景（"把文章 12 设为私密"——
12 出现在**用户消息**里，属证据之一，`_target_evidence` 已经覆盖 user_msg 这一路）。

### D3 动作轮的用户可见文本确定性化（把叙述从"生成"降级为"包装"）

**现状**：写操作的**事实文本**已经是确定性的（`adminops.render_tag_created` /
`render_status_ok` / `reports.py` 三张报表），但**用户最终看到的那一段仍然由 narrator 重写**。
①⑤ 两洞就发生在这个重写动作里：narrator 照抄了工具返回文本里的工具名、把未执行说成已执行。

**目标**：有计划里**真的执行过工具**的轮次（动作/写/数据），用户可见正文 = **系统渲染的确定性文本**；
narrator 只允许追加**一句**人设包装（禁止事实断言），LLM 失败/超时则只剩正文。

**形态选择**（三个粒度，建议从②起步）：
1. 保守：保持现状，只把判据守得更细（**不推荐**——这就是打地鼠）。
2. 分离协议：narrator 输出分两区（`SAY:` 态度 / 事实由系统拼）——改动集中在 model 节点 + server 拼装。
3. 激进：动作轮不跑 narrator（像弹窗那一轮：`pending_confirm` → END 的做法已经有先例）。

**步骤**
1. 先量：从 trace 统计"动作轮回复里有多少字是**事实性内容**"——若大部分轮次的事实都已在
   确定性文本里，narrator 的边际价值就只剩语气，方案 2/3 的观感代价很小。
2. 在 model 节点后加一层**拼装**：`正文 = 确定性事实块 + narrator 一句`（`SAY:` 协议解析，
   不允许出现"已经/完成/成功"族词——这比 8 族判据简单一个量级：**一句话的语法约束**）。
3. 对抗性测试进 CI：喂一个**故意撒谎**的 narrator fixture（输出"我已经建好了"而当轮零执行），
   断言最终用户可见文本仍然如实。**这是 coding agent 靠结构获得、本项目目前靠判据赌的性质**。

**验收判据**：5a/5c/5d/5f 四族判据在真实流量里 **30 天 0 命中**（不是判据变准，是不会再有那种句子）；
对抗性 fixture 测试恒绿。

**风险**：**观感**（回复会变短、变"干"、确定）。这是**最大的一处待拍板**——它改变的是用户
读到的语气与丰富度；技术上反而是减少代码（判据可以退役）。建议先做步骤 1 的量化。

### D1 动作类补齐环境回执（前端回报）

**现状**：导航/特效/夜间/屏幕显示的"回执"是命令帧（`AUTO_NAVIGATE:` / `EFFECT:` / `DARKMODE:`），
**前端执行后没有任何回报**。于是"跳没跳成""特效到底开没开"在系统里没有事实源，
只能靠 `execution_log` 记"已下发"（而下发 ≠ 生效）。

**目标**：前端执行命令后回一条**轻量回执**（成功/失败/用户取消），落 `execution_log`；
没有回报的动作在跨轮记忆里明确记为「已下发，未回报」——**把"未知"如实记为未知**，
而不是让它默认读成"成功"。

**步骤**
1. 前端 `execAgentCommands`（`frontend/public/live2d-widgets/chat-core.js`）执行完毕后发上报；
   通道优先复用现有 `POST /api/monitor/log` 同族的轻量端点（**不新增 SSE 帧**——帧协议改动
   要动三端，见 `__EXEC__` 的教训：只转发不累积、落库顺序契约）。
2. 上报内容：`{cmd, status, ts, conv_id}`，**不含任何凭证**；Rust 侧按会话落库（新列或复用 detail）。
3. 渲染侧：`render_exec_row` 增加"未回报"形态（`跳转「/talk」（已下发，未回报）`）。

**验收判据**：跨轮问"刚才真的跳了吗"能拿到三态之一，且 golden 有断言；
`exec_memory_*` 4 条用例不回归。

**风险**：中-高（跨三端 + 隐私边界：上报是新的写入口，要做限额与鉴权；且"用户取消导航"
会让状态变复杂）。**依赖**：D2 的落库形态先定。

### D2 执行事实类型化（`execution_log` 从"中文一行"到"结构化 + 渲染"）

**现状**：`detail varchar(300)` 写时渲染定稿，同时承担三个角色——用户可读、模型可读、
去重键（读侧按 detail 相等去重 + `（×N）`）。三个角色互相妥协：300 字上限会截断、
去重靠字符串相等（同工具不同目标必须靠渲染文本区分）、**回执帧里其实有**的
`op/article_id/before/after/status/principal_role` 落库时全丢了（Rust 只存渲染行）。

**目标**：落库保留结构化列；读侧注入分两路——给模型的是**紧凑结构化行**，给用户的是中文行
（渲染可以随时改，不改历史数据）。

**步骤**
1. 先做读侧（**不需要迁移**）：Rust `render_exec_row` 已经写时定稿，改不动历史；
   故第一步只能对新数据生效——把结构化字段**塞进现有的 `skill`/`detail` 约定**是错的
   （varchar300 装不下），所以这条的真实第一步是**迁移**：
   `execution_log` 加 `op/target/before/after/status` 列（或 `payload json`）。
2. **按纪律：生产迁移必须由维护者点名「库名 + 迁移文件」**，见 §5 待拍板 ②。
3. 迁移后：写侧双写（渲染行 + 结构列），读侧先只用渲染行（向后兼容），再切结构化行。

**验收判据**：`followup_entity_slot_*` 3 条 + `exec_memory_*` 4 条全绿；
新增"同工具不同目标不误去重"用例（现在是靠渲染文本不同来区分的）。

**风险**：迁移（生产库）+ 跨语言契约（Python 写 / Rust 读，`digest` 的同族风险：
改一侧必须同步另一侧 + `tests/test_entities.py`）。

## 6. 明确不做的事（防范围蔓延）

- **不换模型求稳**：8 个洞里 3 个是系统自己喂错数据/读错字段，换模型一条都修不掉。
- **不引入第三方 agent 框架**：现有拓扑（planner ⇄ execute → model → gate）与
  checker/receipts/refs 已具备所需结构，问题在**数据契约**不在编排。
- **不为判据加更多词表**：先减后加（D6 的 KPI 就是不许加）。
- **不做会话控制类新功能**（取消/重做/多任务并行）——不在本轮范围。
- **不动 `authz_enforce` / `_HARD_SCOPES` / 写工具 fail-closed 纪律**：
  `uid<=0` 不发请求、HTTP 200 不算成功、"没做成"必须 `unavailable`——这三条是今天唯一没出事的层，别碰。

### 附四：id 不是同一套（20260924，P3 方向的第三次加固）

**现场**（trace `20260924T030031`）：河灯留言的审核终态通知里给的是 `/guestbook?lid=96`
这样的定位链接，planner 拿这条通知里的 **96** 去读文档：

两次（96 / 95）都只拿回一句「未找到该文档」，narrator 于是把结论写成"这两条留言拿不到内容"，
而主人问的是"这两条是什么"。**错的不是模型**：那个 id 是**留言 id**，它确实不在公开留言

身份回落）与"是不是主人点的那一个"（附二⑨），这一次是"这个 id 属于哪个命名空间"。

**这一轮做的（②话术 + 它捎带的 kind 语义）**：

| 落点 | 内容 |
|---|---|
| `tools/base.py::_get` | 新增 `not_found_text` 参数：**HTTP 404 从此与"服务挂了"分家**——带话术的调用点拿到 `not_found`（checker 判 BLOCK + 原因码 `target_not_found`，过程行「目标不存在」），不带话术的调用点语义不变（仍是 `unavailable`）。两族的**应对是相反的**：查无此物要换 id 或如实问主人，服务不可用才"稍后再试" |
