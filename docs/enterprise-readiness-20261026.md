# 企业落地验收矩阵：2026-10-26

当前项目具备标准框架、领域工具、授权确认、幂等账、检查点、CI与追踪基础，
适合继续做单站、低流量、人工确认下的受控试点。125项行为回归通过不能替代完整语义质量、
真实批准写入闭环或持续生产运行指标。视觉按维护者要求排除主评测，不属于本批支持承诺。

企业没有统一的“达到多少分即可上线”。目标应根据业务风险、用户体验、预期负载和成本约定，
并同时验证上线前回归与上线后的质量。下面数值是针对本项目的**建议初始目标**，不是行业硬标准。
参考[Google SRE的SLO方法](https://sre.google/workbook/implementing-slos/)、
[LangSmith评测分层](https://docs.langchain.com/langsmith/evaluation-types)及
[NIST生成式AI风险管理](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf)。

真实任务成功的分母应限定为已声明支持、输入与必要确认齐全的任务；正确拒绝越权或不存在目标
可作为相应用例的成功。角色扮演的语气与虚构表演，不和账号、规则及执行事实混成同一种事实性指标。

## 现有评测资产

- 请求级线上基线、真实模型配合隔离业务的确认回放、确定性CI均已具备。
- 词法检索已有recall@k、MRR等评测入口及离线检索评测；本批没有重新测量，不能填入当前线上成绩。
- LLM judge已有代码和小量材料验证，尚未成为完整任务语义质量的可靠分数。
- 原生trace有调用、预算、缓存、进度和恢复数据。现有日报/部分旧图告警不等于企业级SLO闭环。
- 真实身份覆盖超级管理员、普通用户和杂鱼；普通管理员、失效凭据、跨用户与权限变化场景需要单列验收证据。

## 优先补齐的工作

1. **任务语义与评测器校准**：选100–200条人工标注材料，覆盖成功、虚构规则、错误目标、
   不必要澄清、合法no-op、角色/称呼和未知结果。分别量judge误报、漏报；核对工具事实、
   待确认内容及最终业务状态。真实数据交给外部评审需遵守已授权范围，不能默认扩大。
2. **重复稳定性与真实端到端**：先选20–30个核心任务，每项独立5–10次；补长对话、
   受控真实批准写入与浏览器操作，分别统计成功率、错误写入与用户介入次数。
   这批规模是启动建议，仍不足以单独证明极低故障率。
3. **容量与故障演练**：按实际预计流量设并发档位，验证时延、取消释放、上游429/超时、
   后端失败、进程重启及数据库恢复。优先建立原生指标告警和操作处置记录，复用现有追踪。
4. **真实成本与持续质量**：采集服务商实际扣额或对账数据，按成功任务统计成本；
   对真实流量做合规抽样、坏例回流及版本回归，明确SLO、错误预算和告警处理责任。

这些工作以验收与运行证据为主，优先复用现有框架、追踪与测试入口，按实际业务范围补齐。
物联网仅作为可关闭的演示模块；正式交付范围应按实际安全与维护承诺界定。
