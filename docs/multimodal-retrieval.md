# 多模态检索：分阶段方案与判据

> **状态**：搁置（20261005），方向认可、条件未到。取舍与重开条件见
> [adr/adr-0005-multimodal-retrieval-deferred.md](adr/adr-0005-multimodal-retrieval-deferred.md)。
> 这份文档是那份 ADR 的展开：**真到要做的时候，按这里的顺序做，别从第 2 期开始**。

## 0. 先说清楚"多模态检索"在这里指什么

这个仓里有**两个**消费面，需求不一样，很容易被当成一件事：

| 消费面 | 入口 | 今天是什么 | 加图之后想要什么 |
|---|---|---|---|
| 站内检索框 | 博客前端 → Rust `/api/notes/search` | 文章标题/正文的关键词检索（`search_score` 相关度排序） | 图也能被关键词搜到（"夜景"、"架构图"）；**不要求**以图搜图 |
| agent 对话 | 看板娘 → Rust → 本仓 | `rag_search`（BM25 + 可选向量路）定位文章，**图不在检索池里** | 用户上传一张图问"这个怎么做"时，能检索到相关文章；以及"有没有跟这张像的"（**这是最远的一期**） |

两个面共享同一套前置件，但**不共享实现**：检索框那侧在前端+Rust，agent 这侧在本仓。
把它当一件事规划，最后一定是"在 agent 里做完了、检索框还用不上"。

## 1. 现状（20261005 逐条核实）

| # | 事实 | 出处 |
|---|---|---|
| 1 | **对话里看图已经能用**：用户上传的图拼成 `image_url` 内容块送进模型，多图 ≤6 张、单图 ≤1.6M 字符 | `server.py::MAX_IMAGES` / `_build_messages` |
| 2 | 图片块拼在消息**尾部** ⇒ 前缀零污染，prompt 前缀缓存命中不受影响 | `server.py` 同处注释 |
| 3 | **确定性层看不见图**：`_msg_text` 只取 `text` 块——意图分类/指代锚点/重复拦截都是纯文本函数 | `agent/context.py::_msg_text` |
| 4 | **检索层看不见图**：BM25 与向量路都吃文本；图片没有任何文字字段 | `rag/search.py` |
| 5 | **图片不进对话历史**：Rust 落库把图换成一串标记，图片本体不入库 | Rust `chat.rs` |
| 6 | 图片存在上传目录、由公开读前缀提供（`/api/protect/download/`） | 父仓 `uploads/` + nginx |
| 7 | 站内图片共 **19 张** | 上传目录计数 |
| 8 | 全仓**没有任何**视觉/多模态代码或依赖 | `pyproject.toml` 的 11 个依赖 |

第 3、4 条经常被误读成"图片被丢掉了、所以模型看不见图"。不是：**模型看得见图**（第 1 条），
被丢掉的只是喂给确定性纯函数的那一份（第 3 条），以及检索索引里的那一份（第 4 条）。

## 2. 为什么 caption 是前置，而不是可选项

三处缺口全都指向同一件事——**图片需要一个文字化的身份**：

1. **检索**：BM25 与向量路都是文本管线。图片没有文字 ⇒ 索引里没有它 ⇒ 检索不到。
   给图配一段文字描述，**现有两条路一行不改**就能搜到它（这是投入产出比最高的一格）。
2. **跨轮指代**：历史里只有"上一轮有图"这个事实（第 5 条）。要让模型说得出
   "你刚发的那张架构图"，它得有一个稳定的指称——caption（或图 id + caption）就是它。
3. **判据**：没有文字表征，"这张图检索得对不对"**造不出评测集**。
   有了 caption，就能像今天对待文章一样：写 query、写期望命中的图 id、量 recall@k。

反过来说，**没有 caption 就直接上联合嵌入空间**，是在错的路上一路加速：
它跳过了"图片到底有没有值得被检索的内容"这个问题，而这个问题在 19 张图上
根本回答不了——先有 caption，才知道站内图片里到底有没有可检索的信息量。

## 3. 分期

每一期都以**可观测的触发条件**开头。条件没到就别提前做——同族教训见
[rag-design.md](rag-design.md) §8 的触发条件表。

### 第 0 期：图片入库即产生 caption（**重开时的第一步**）

- **触发**：**任何**图片相关需求被真正提出时（含"检索框里搜不到图"这条最常见的）。
- **做什么**：图片落库路径上生成一段文字描述，落成字段（与图片行同表或邻近表）。
  生成方式按当时的成本选：远端视觉模型批量补跑一次即可，19 张图是分钟级的事。
- **做在哪儿**：**不在本仓**。图片上传/入库在 Rust 与前端那一侧，本仓只是消费方。
  本仓要做的只是把 caption 当成文章正文之外的一份可选语料。
- **判据**：站内每一张图都有非空 caption（可机械核对"有图无 caption 的行数 = 0"）。
  这条判据要**跑在 CI 或夜间**，否则新上传的图会静默地不进索引——这正是本仓
  最熟的那类失效（"看着在跑、其实没跑"）。

### 第 1 期：文字检索覆盖图片（**大概率够用的一期**）

- **触发**：第 0 期完成。
- **做什么**：把 caption 作为一篇"文档"喂进现有检索路，命中即返回图（带所属文章/说说）。
  检索框那侧与 agent 那侧**各自接**：前者在 Rust 的搜索里，后者在 `rag/search.py` 的语料里。
- **不做什么**：不动 `_CLIFF_RATIO`、不动 BM25、不加新的打分参数。
  这一步的全部内容是"语料里多了一种文档类型"，不是"换一套检索算法"。
- **判据**：新增一组以图为中心的 query（含"夜景/架构图"这类只有 caption 才有的词），
  在 `eval/recall_eval.py` 同口径下量 recall@k / MRR / 噪声率；**同时**要有一条反控——
  原有文章 query 的读数**一个都不许变**（图片进池不许挤掉文章候选）。
  两臂各自跑完，报告落 `eval/report/runs/`。
- **风险**：图片语料会稀释文章候选的分数（候选变宽是已知的下游影响）。
  量的方式与混合检索那轮一样：看 `mean_candidates`，别只看通过率。

### 第 2 期：联合嵌入空间（**只在触发条件满足时做**）

- **触发（两条同时满足）**：站内图片 **≥1000 张**，**且**出现"没有文字可概括"的查询
  （以图搜图、或者描述不出关键词的图）。
- **做什么**：把图与文映射到同一向量空间，检索时图文可互相命中。
  本仓的落点很明确：`rag/vector_index.py` 已经有内容寻址的 chunk 键、原子落盘、
  RRF 融合与降级路径——**扩的是 embedding 的输入类型，不是重写检索**。
- **代价（要先认下来）**：联合嵌入的端点与 OpenAI 兼容的文本 embeddings 不是同一条路径，
  配置要**第三份**（今天已经有两份：LLM 的 `*_API_KEY` 与检索的 `EMBEDDING_*`）。
  多一份配置就多一个"改一处忘另一处"的形状，ADR 里要写清谁说真话。
- **判据**：与第 1 期同口径，但**必须两臂并跑**（caption 文字路 vs 联合嵌入路）。
  单臂读数在这件事上没有意义——全量两跑红集零交集就是噪声，这条教训本仓已经吃过。

### 第 3 期（可能永不做）：以图搜图的产品化

- 触发：第 2 期落地**且**有真实使用。这一期是产品决定，不是技术决定：
  站内检索框目前**允许匿名**（访客标识只做去重），而"以图搜图"是在公开面上
  开一个每请求都要跑一次视觉模型的入口——**要不要登录、要不要限流**，得先拍板。
  技术上能不能做不是问题，成本能不能被匿名流量接受才是。

## 4. 与本仓架构的两个具体咬合点

真做的时候会撞上这两处，先写下来省一次排查：

### 4.1 用户上传的图没有 `$tool[N]` 引用 ⇒ 必须由系统注入

planner 填参数的通道是"引用某个工具返回里的字段"（`$tool[N].field`）。用户刚上传的图
**不属于任何工具返回**，planner 无从引用它。所以图片必须走**系统数据**那条路——
和 `article_id` 今天的位置一样（`read_article` 技能对 planner 不可见，参数由系统注入）。
规矩：**planner 不能填 URL**。让它填 URL，就会有模型编一个 URL 的那一天。

### 4.2 用户图不能当检索语料（但可以当**查询**）

图片进检索池是第 1 期的事（caption）；用户当下上传的图是**查询侧**，
两件事别混。混了以后会出现"用户发的图被当成站内内容返回给他自己"这种形状。

## 5. 本机硬约束（不是偏好，是不可行）

| 约束 | 取值 | 影响 |
|---|---|---|
| 可用内存 | ~1.5GB | 本地视觉模型不可行 |
| swap | 3979 / 4035MB（近耗尽） | 同上，且任何"先跑起来看看"的尝试会拖垮生产机 |
| 磁盘 | 约 3.5GB 可用 | 图片与向量产物都要算进这一格 |
| 本机 = 生产机 | — | 不许 `cargo build --release`、不许 `uv sync`、不许并发重活 |

外部服务在**本机进程**之间是"谁都到得了"的，但浏览器到不了 `127.0.0.1`——
所以任何新的 Agent 能力，暴露到前端的那一段**必须由 Rust 代转**，本仓只提供回环接口。

## 6. 评测数据从哪来

到第 1 期时，"图片检索得准不准"需要一组 query↔图 id 的配对。公开数据集帮不上忙
（它们量的是检索器的通用能力，不是"你这 19 张图排得对不对"），正确做法是**自己造**：

- 从站内图片出发写 30–100 条 query（含只有 caption 才答得出的那种），人来过一眼确认期望值；
- 用 `eval/recall_eval.py` 的同一套口径量（**评测即线上实现**，不另写脚本）；
- 合成 query 一定要人过一眼，否则就是自证。

数据集选型与工具（C-MTEB 的中文检索集、`ranx`、`pytrec_eval`）见
[rag-design.md](rag-design.md) §9——那一节的结论对本节同样成立：公开集用来横向量模型与
调融合参数，不用来给站内搜索打分。

## 7. 判据

第 0–3 期各自的判据写在上面每一期里。跨期共用的三条（重开这份文档时先看这里）：

1. **每一期都必须有"它没生效"的判据**。本仓的空断言清单
   （"模块能 import"、"函数返回 list"、"目录建出来了"）在这里同样适用：
   "图进了检索池"这句话的判据是**一条只有图能命中的 query 真的命中了图**，
   不是"索引构建时没有报错"。
2. **判据要能在 CI/夜间跑**，否则新图会静默地不进索引。
3. **两臂并跑、读计数不读通过率**（同 [toolcall-stability-roadmap.md](toolcall-stability-roadmap.md)
   与 L1 的口径）。
