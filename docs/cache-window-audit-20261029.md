# 短对话缓存与历史窗口审计

## 生产证据

2026-10-29 的 `conv_320` 共20次主对话调用：输入183,418、缓存读取127,872、
未缓存55,546 token，整体命中69.72%。两次独立摘要调用输入2,774，缓存读取0。
统计取自 `native.llm_done` 与 `summarizer.llm_done`，输入是含缓存部分的总量。

系统、工具目录与会话头指纹保持不变，多次短对话的历史开头变化，连续相同消息只剩
系统消息。01:35:04 输入9,233、命中8,320；01:36:05 历史裁剪后输入9,257、命中6,912。
01:27:52生成摘要后，01:34:40仍命中8,192；摘要生成不等于主对话缓存被清空。
01:42:41生成摘要后的下一轮也发生历史裁剪，不能只按时间相邻归因摘要。

## 修复与边界

- 常规提示词窗口在 checkpoint 消息元数据中记录边界，达到原有1,800估算token上限时，
  分批收缩至约1,200，留出增长空间。完整 checkpoint 的5,400上限不变。
- 完整请求预算装配保留固定账号消息位置；动态页面、摘要和当前状态继续放在最近完整
  问答之前。最新长问答、来源工具配对、权限过滤、当前输入及输出预留继续生效。
- 增加匿名消息规模与窗口变化观测；没有改变摘要频率、工具激活、模型或会话路由。

## 实际 API 最小对照

OpenCode Go、`deepseek-v4.1-flash`，42项相同工具定义、`tool_choice=auto`、
思考关闭、相同会话头。八次合成请求，没有执行工具，也没有发送生产对话。
两组均使用修正后的固定消息布局，只改变历史窗口策略；采用交替顺序调用。
捕获实际HTTP请求体哈希与原始usage，原样重复请求哈希相同，SDK与原始输入计量一致。

| 场景 | 滑动窗口：总输入 / 未缓存 | 分批窗口：总输入 / 未缓存 |
|---|---:|---:|
| 原样重复 | 8,645 / 69 | 8,095 / 31 |
| 追加短对话1 | 8,645 / 1,733 | 8,205 / 397 |
| 追加短对话2 | 8,645 / 1,733 | 8,315 / 379 |

两次追加的平均未缓存输入1,733→388（减少77.61%），命中79.95%→95.30%，
总输入17,290→16,520。样本只验证窗口策略在该负载下的收益，不代表线上整体、
长任务、压缩边界或服务商缓存保留的保证。

另十次 `tool_choice=none` 探针出现相同输入布局下约2K/8K的输入计量差异；
未据此计算优化收益，也不与生产auto模式混用。当前证据不能确定其上游内部原因。

原始匿名用量、HTTP哈希和探针脚本留在运行机 `/tmp/saudade-cache-window-*`。
离线验收包含45轮真实框架接续与重载、窗口回收、摘要变化、来源配对和权限变化。
干净检出完整回归1,877通过、12项因缺少显式集成依赖跳过；前端16项协议测试通过。

缓存依赖已持久化前缀的完整匹配，且是尽力而为；参见
[DeepSeek官方说明](https://api-docs.deepseek.com/guides/kv_cache/)。
