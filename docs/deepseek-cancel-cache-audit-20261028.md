`deepseek-v4.1-flash`、low。审计不修改模型配置、工具权限或业务数据。

## 原请求的证据

维护者报告的被取消调用：未缓存输入 4,002、缓存读取 2,048，总输入 6,050，
命中率 33.85%。这是控制台材料；应用因断连没有收到该调用的最终 usage。
不能把应用侧缺失读数当成零，也不能用恢复请求的 usage 回填原调用。

同一会话的上一轮长答、被取消的闲聊、显式恢复三者均使用 `1b1d722`。对照结果：

| 阶段 | 工具定义 | 消息 | 与被取消调用的关系 |
| --- | ---: | ---: | --- |
| 上一轮长答 | 30 | 13 | 工具和历史前缀不同 |
| 被取消调用 | 25 | 20 | 用户报告缓存读取 2,048 |
| 同任务恢复 | 25 | 20 | 全部消息、工具、会话亲和与推理档位指纹一致；API 输入 6,050、缓存读取 6,016，命中 99.44% |

新 25 项工具与旧 30 项的前 25 项定义逐项一致，不是随机重排或部署导致变化。
上一轮恢复了 `admin_reports`，多出五个报表读取工具；下一轮不再恢复该领域。
新一轮的历史消息开头也变化；按整条消息指纹比较，连续相同的只有系统消息。
上一轮与被取消调用均为 `needs_summary=false`，没有摘要模型调用。
本次历史窗口变化不能归因为这两轮生成了新摘要；裁剪保留窗口与生成摘要是两种操作。

代码路径为：历史预算裁剪 → 保留的工具观察变化 →
`ToolSession._restore_domains()` 推断需恢复的领域 → 当前工具菜单变化。
因此，历史数据窗口与工具加载状态的生命周期存在耦合；它会让跨轮请求失去部分热缓存前缀。
这是可优化的应用侧触发因素，不能把所有未缓存 token 精确归因给它。
checkpoint 恢复的是已提交的节点与任务状态，被取消的模型节点仍需重新调用；
缓存复用输入前缀，并非接回被取消 HTTP 响应的下一个 token。

SDK 与原始 `prompt_tokens`、`cached_tokens`、输出和推理计数逐项一致。

只改变工具目录、不打断的单变量对照，消息、会话头、生成参数均相同：

## 归因与边界

- 前端与宿主：取消关闭流，恢复沿用原会话和任务；原请求的恢复模型消息没有被重新构造为新任务。
- Agent：恢复保留原模型输入。跨轮历史裁剪与领域恢复联动会改变新请求前缀，是明确的应用侧影响因素。
- SDK 与统计：本次原始 HTTP usage 和 SDK 读数一致，未发现本地把未缓存输入误当总量。控制台 Input 与 Cache read 分列，比例分母必须两者相加。
- 服务商：低命中值由上游报告；固定请求的正常首发也可能低命中，再发变热。本次未复现打断清空热缓存，但无法区分 OpenCode 路由、DeepSeek 持久化和缓存淘汰各自的内部贡献。

[DeepSeek 缓存说明](https://api-docs.deepseek.com/guides/kv_cache/)描述已持久化前缀单元的完整匹配、
公共前缀识别、构建延迟与尽力而为策略。
[OpenCode Go 契约](https://opencode.ai/v2/docs/console/go/#where-can-i-use-it)要求会话保持稳定的
`x-opencode-session`。当前实现及实际 HTTP 对照满足会话亲和要求；这不是命中率保证。

另一个独立问题是取消延迟：原连接在约 2.02s 结束，后台模型调用到约 5.83s 才退出，
运行资源随后释放，断连后多占用约 3.84s。同步流在下一个回调检查停止标记，不能立即中断
正在等待的上游读取。这段等待不证明模型一直生成或已停止计费，需以上游账单为准。

原始材料留在运行机 `/tmp/saudade-deepseek-cancel-cache-audit-20261028/`，包含
`wire-probe.json`、`wire-probe-auto.json`、`wire-schema-transition.json`。
生产会话原文和认证信息没有提交到本报告。
