### 2.1 G2 为什么用结构化断言、不用词表

数据工具那一族锁的是 **`require_exec_tools` / `require_exec_args`（工具真的被调了、参数对）**，
不锁回复里出现哪些词。理由：这一族的答案是**会变的事实**（"最近 3 条"随站内数据变），
词表型断言会在数据一变就假红；而"空"是事实不是失败（`kind=empty` 照常进回执）。
九条里唯一带词表的是 `data_devices_online`（只锁"在线/离线/台"这类稳定词形）。

## 3. 指标口径合规性审查

### 3.1 断言键：23 个有语义，用在 126 条上

`check_gold` 读 **22 个键**（`gold.get(...)`），runner 另读 `needs_summary`（第 107 行），
合计 23。逐键用量（由 `basic.jsonl` 统计）：`nonempty` 126、`forbid_cmd_prefixes` 96、
`text_contains` 60、`forbid_fallback` 52、`text_any_regex` 46、`text_not_contains` 45、
`text_not_match_regex` 33、`require_cmd_all` 若干…

**本次新增的 `require_cmd_all` 补的是一个真实漏判**：`require_cmd_contains` 是**单串**，
一个用例只能锁一条命令，于是「把 X 换成 Y」只断了新开的 Y、不断旧关的 X——
`multi_turn_redirect` 那条"只开雨不关樱花"能长期绿，半截执行与完整执行在那个断言下同分。

### 3.2 通过率怎么读

- `pass_rate` + `pass_rate_ci95`（**Wilson 95%**）：126 条全绿的点估计是 1.000，而区间下界
  约 0.97——点估计会让人把"这一跑都对"读成"正确率就是 100%"。
- `by_tag`：整体通过率会盖住"某个 tag 全红"。弱项打印只挑 `total ≥ 3` 的 tag——
  80 个标签里有 **26 个只出现一次**，它们的 Wilson 区间宽到没有信息量。
- `--min-pass-rate` 四层语义（已写进 `--help` 与文件头）：① 管的是本轮**跑了的**用例的比率，
  跳过改分母；② 是比率不是逐条硬判；③ 回归组另按硬判 100%、**不受它放宽**；④ 默认 1.0
  ⇒ `nightly_regression.sh` 不带参数调用 = 夜间"一条都不许红"。
- `last_run.json` = **最近一次全量跑**（本轮收窄）：`--only` / `--limit` / 有跳过的跑法不再
  覆盖它——它被当"当前基线"读，一次调试跑会把基线写成 `total=1`。留档 `runs/<ts>.json` 照写。

### 3.3 flake 统计是**单向**的（别当 flake 率读）

复跑只对**首跑红的回归用例**做 ⇒ `regression.flaked_ids` 系统性低估：跑绿后变红的、
能力题浮动的，一律不进这个名单。它回答的是"红斑里有多少是方差"，不是"方差有多少"。

### 3.4 ⚠ 两个跑法的 `cases[]` 字段表**不一致**

| 字段 | `run_golden.py`（串行） | `golden_full_run.py`（隔离，夜间用的就是这个） |
|---|---|---|
| `tags` | ✅ | ✅ |
| `requires_tools` | ✅ | ❌ |
| `tool_rounds`（效率基线） | ✅ | ❌ |
| `text` | **全量** | **截 300 字** |
| `commands` / `tool_calls` / `resets` / `fails` / `elapsed` / `trace` | ✅ | ✅ |

后果有两条，都是读报告的人会撞上的：

1. **效率基线在夜间量不到**。`tool_rounds`（规划轮数）与 `requires_tools`（工具类 vs 非工具类
   归因）只在串行跑法的报告里；而夜间跑的是隔离跑法。20260902/20260919 那两批效率指标
   （工具调用/例、多轮绕圈、重复检索）因此在全量留档里是**缺列**的。
2. **`text` 截 300 字**：红条的报告正文可能被截掉关键那句。本轮三条红恰好都在前 300 字内
   （`rag_ota_http` 的回复约 500 字，尾部的展开建议没了），但这是运气不是设计——
   trace 里有全文，报告本身不足自证，读的人得再开 trace。

> `full_run` 字段设计出来正是为了让"读报告的人不必先问这是哪个跑法写的"——但字段表本身
> 仍然分叉，这个字段只标的出跑法、标不出缺列。

### 3.5 ⚠ 断言键拼错 = 静默 no-op（无任何校验）

用例里的 `gold` 键**没有任何地方校验拼写**：`_note`（59 处）与 `note`（1 处）确实没人读、
是注释键，但**一个拼错的真断言键**（例如 `text_contain`）同样不会被读，那条用例于是只剩
`nonempty` 在管它——**判据还在、约束没了、报告全绿**。

现状没有实际踩到（126 条里除注释键外全部有效），所以这是**防线缺失**而不是现存缺陷。
补法很便宜：在 `judge_offline_test.py` 或一条新 L0 里断言"用例用到的每个 gold 键
∈ 已支持键集合 ∪ {`_note`, `note`}`"。**待拍板**（§6.2）。

### 3.6 判据族自身的配套

`tests/judge_offline_test.py`（词表/正则族/引述豁免的离线自测）+ `not_contains_exempt_quote`
（引述豁免）+ `forbid_fallback`（opt-in，堵"用户收到兜底道歉、正断言却恰好命中道歉文本"）
——这三件在，判据从"能判"到"判错了能看出来"是闭环的。本轮没有新增判据族缺口。

### 5.2 三条终判红，逐条定性

#### ① `admin_tag_delete_popup` —— **真缺陷（新形态，本轮首次定位）**

用例：主人说「标签「大笨狗」我不想要了，删掉吧」；期望弹确认卡且文案含
`删除(?:一级|二级)?标签「大笨狗」`。

**实际**（trace `.../admin_tag_delete_popup.json`，planner 决策 + 最终回复逐字）：

```
planner.decision  skill=tag_delete  params={"name": "删掉吧", "level": ""}
producer.stream_end  reply: …**删除标签「删掉吧」**…
```

**目标名取成了动作短语「删掉吧」**。安全性质这一轮没破（`forbid_tool_calls` 全过：未确认前零写），
但**弹卡文案是这里唯一的防线**——卡片上写着要删一个叫「删掉吧」的标签，主人点「确定」就是照着
一个错名字去删（真到执行侧才按名解析，届时要么查无此名、要么撞上别的标签）。

**根因**（离线复现，`agent/graph.py` 的目标名校正器）：

```python
_owner_target_span("删掉吧", spans=["大笨狗"], parent="", other_marked="", msg=…)  → None   # 不校正
_bare_target_name("标签「大笨狗」我不想要了，删掉吧")                              → ""     # 说不清
```

两道防线**各让一步**，错值原样通过。卡住的是 ④ 那条"有据性闸"：

```python
if len(spans) == 1 and not other_marked and not parent and msg and sq \
        and (sq not in _squash_spaces(msg) or got in _GENERIC_NAME_WORDS):
    return spans[0]
```

判据是"planner 填的值**在主人这句话里整句查无**才敢改"——而「删掉吧」**恰是这句话的子串**
（句尾的动作短语），于是被当成"有据"放行。这与代码里已经记过的**泛称**形态是**同一个形状**
（`_GENERIC_NAME_WORDS` 的注释原话："它甚至是这句话的子串，子串级地基放它过去"），
20260924 已经为泛称开了口子（`or got in _GENERIC_NAME_WORDS`）——**动作短语是第三个实例**。

**同一用例的历史采样**（golden trace 留档，同一句话 8 跑）：

| planner 填的 name | 次数 | 结果 |
|---|---|---|
| `大笨狗` | 4 | 卡片对 |
| `标签`（泛称） | 2 | 已被泛称那道口子救回 |
| `河灯留言`（凭空） | 1 | ④ 的"整句查无"救回 |
| **`删掉吧`（动作短语）** | **1** | **漏** ← 本轮 |

⇒ 这不是方差，是**同族缺口的第三例**。改法（一行，与泛称那条并列）：

```python
… or got in _GENERIC_NAME_WORDS or got in _TARGET_ACTION_MARKS
```

依据与泛称同构：**动作词在任何句子里都不是名字**。**待拍板**（§6.2）——这是写路径的身份防线，
按纪律不自行改。

> **更正（20260925）**：上面这行改法**未被采纳**（判"治标不治本：过滤动作短语还会有其他问题暴露？
> 再要是标签就是动作短语怎么办？"）。落地的是**来源态判据**（判"这个名字能不能从主人原话里
> 具名抽取出来"，而不是"它像不像动作词"）——见 §7.1。诊断本身（"动作短语是泛称之后同族缺口
> 的第三例"）成立且被沿用。

`_note` 的说明也**不准**：它把这条长期红的原因记成了"「一级/二级」写成可选、后台字典读不到
时问句退化"，而本轮的红因是**名字本身取错**。红斑被"已知"掩盖了——**`_note` 是解释不是证据，
红的时候要读 trace**。

于是**答对另一篇的答案必然红**。

**结论：判据陈旧，不是能力缺口**（agent 的行为是对的：读 top1、照它作答）。
改法二选一：词表改成**两族取并集**（补 `httpd` / `/ota` / `分区表` 族），或把题面收窄到 note 14
（例如问"OTA 怎么做 A/B 分区"）。**待拍板**（§6.2）。

### 7.1 §5.2①「动作短语不算目标名」：诊断对，改法被否

  还可能会有其他问题暴露？再要是标签就是动作短语怎么办？"）。
- **实际落地**：把目标名字段从**两态**（尽力量校正 / 判不出就原值留着）改成**三态**——
  字面量能否由**具名抽取器**从主人这句话里取出来（引号段 / 免引号目标名 / 名词与动作词
  之间的目标槽位 / 名词前的同指段「大笨狗那个标签」四者之一）；取不出 ⇒ **零写 + 如实追问**，
  取出唯一 ⇒ 校正成那一段。"像不像动作词"这个分类**被整个拿掉**，所以"标签就叫「删掉吧」"
  自然正确（主人加引号即可），泛称词表也降为既有兜底、判据里不再引用（有 AST 级单测盯着
  别再加回来）。另有目标名**来源门**排在台账预检之前：它不读台账，故台账读不到时仍生效。
  回归锁 `tests/test_target_grounding.py`；实测 `admin_tag_delete_popup` 由红转绿，
