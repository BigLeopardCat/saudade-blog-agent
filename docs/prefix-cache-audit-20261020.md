# 前缀缓存审计：50.1% 的命中率是"整段冷启动"，不是"槽位站错位置"

**一句话结论**：planner 每次调用送 **52,145 tok**，其中 **39,319 tok（75%）是技能 schema**、
只有 12,826 tok 是提示词正文。而正文里**第一个会变的字节在第 94.8% 处**（`round_info`）——
所以"把 `page_ctx` / `round_info` 挪到静态头之后"**最多省 1.3%**。

**真正的大头在 schema 里，而且正好是一半**：**41,499 字符（schema 的 50.2%）是散文**，
不是签名——它描述的是"这个站能干什么"，**那是一份内联的目录**。
其中 `intents` / `reply_kind` 两格被逐字抄进了 49–50 条技能：**只搬描述文本**
（结构留原地）能省 20,352 字符 ≈ **−18.1%**（§4②）；把整份散文挪到
`describe_skill` 后面能到 **−34.6%**（§4④）。

命中率那一侧：**双峰分布**，42 次命中 ≥90%、33 次命中 <1%，
**80% 的未命中 token 全在那 33 次整段冷启动里**，而冷启动**与间隔不成单调关系**
（62 秒可以全冷、120 秒可以全热）⇒ 不是 TTL，是**共享网关上被别人挤掉**，我们控制不了。

> ### 更正（20261020 晚）
> 本篇初版说"`page_ctx` 站在第 16,633 字符处 ⇒ 它后面的一切永远进不了缓存 ⇒
> 每次未命中 23,505 应该掉到 1,055"。**那个模型漏掉了最大的一块**：`input` 里
> 一半以上是**不在提示词文本里**的 tools schema。按实测重新定价，重排的收益是
> **~1.3%，不是 ~43%**（差 33 倍）。§1–§3 是重写过的；§4 的修法仍然成立，
> 但**它的理由从"省钱"降级成"卫生"**。

## 1. 一次 planner 调用到底装了什么

两个角色、两条方程解出"正文"与"schema"各自的 tok/字符（`/tmp/solve_split.py` 的做法）：

| 角色 | 正文 | schema | 实测输入 |
|---|---|---|---|
| `admin` | 23,477 字符 → **12,826 tok（25%）** | 82,612 字符 → **39,319 tok（75%）** | 52,145 tok |
| `user` | 18,300 字符 → **9,998 tok（53%）** | 18,681 字符 → **8,891 tok（47%）** | 18,889 tok |

解出 **正文 0.546 tok/字符、schema 0.476 tok/字符**。admin 的 schema 是
**52 条技能、每条约 1,590 字符**，均匀分布（最大的 `task_hold` 3,371 字符、4.1%；
最小的 `task_drop` 392 字符）——**每问一句"你好"都要把 52 条技能的完整 JSON 送一遍**。

这也解释了 trace 里那两种输入尺寸：`conv_*` 是 admin（52K），
`user_1_*` 是 user 角色（18.9K）。

## 2. 正文里第一个会变的字节在第 94.8% 处

实测渲染（admin，10 轮历史），逐槽位定位：

```
        0 ─ 21,810   静态头：规则 + 技能菜单(workflows_context, 4,899 字符) + tools_desc + max_rounds
   21,810            page_ctx     ← 含 current_time=…13:16（分钟精度）
   22,253            round_info   ← 「当前决策：第 N/4 轮。本轮已有/尚无工具执行帧」**每轮必变**
   22,278            recent_context
   22,287            user_msg
   22,300 ─ 23,477   其余
```

**首个差异字节在第 21,957 字符处**（就在 `page_ctx` 的分钟数字上），
而 `round_info` 在 22,253 —— 占 23,477 的 **94.8%**。

⇒ 重排（静态块全部前置）**最多**把这 5.2% 的正文变成可缓存前缀：
`23,477 × 5.2% × 0.546 ≈ 669 tok`，占 52,145 输入的 **1.3%**。

**而且 `page_ctx` 里只有 `current_time` 是分钟级**：同一分钟内的两次调用
（trace 内相邻轮）它**根本不变**，实测 `13:21:08` 与 `13:21:41` 两次的 `page_ctx` 逐字相同。
所以 §4 的修法在真流量里的实际收益比 1.3% 还要小。

## 3. 命中率是双峰，冷启动不是 TTL 造成的

近 6 天 92 次 planner 调用（`logs/agent/traces/**`）：

| 档 | 次数 | 说明 |
|---|---|---|
| 命中 <1% | **33** | 整段冷启动，含 21 次 `cache_read=0` |
| 命中 1–50% | 12 | 纠偏轮 / 换模型那一轮 |
| 命中 50–90% | 5 | |
| 命中 ≥90% | **42** | 稳定在 48,592–53,248 |

合计 输入 4,333,401 / 命中 2,170,864 = **50.1%**；
而未命中 2,162,537 里 **33 × 约 52,500 ≈ 1,732,500，即 80% 全在那 33 次整段冷启动**。

**冷启动与时间间隔不成单调关系**——这是判定成因的关键读数：

| 间隔 | 结果 |
|---|---|
| 2.5 秒（trace 内相邻轮） | 命中 |
| 58 秒（13:16:41 → 13:17:39） | 命中 |
| **62 秒**（08:43:31 → 08:44:33） | **全冷** |
| 89 秒（13:17:39 → 13:19:08） | 全冷 |
| **120 秒**（13:22:43 → 13:24:43） | **命中** |

62 秒可以全冷、120 秒可以全热 ⇒ **不是 TTL**，是容量淘汰。opencode zen 是**共享网关**，
上游的 context cache 挂在**账号**上，我们控制不了谁在挤。

**第二个成因是换模型**：两天里生产跑过四个模型，**每个模型一份独立的缓存**。

| 模型 | 调用 | 输入 | 命中率 |
|---|---|---|---|
| `deepseek-flash` | 8 | 290,823 | **84.5%** |
| `deepseek-v4.1-flash` | 34 | 1,811,474 | **61.5%** |
| `minimax-m3.1-flash-free` | 30 | 1,288,396 | **43.5%** |
| `longcat-2.5-preview-free` | 16 | 732,916 | **21.0%** |

**每换一次模型，前缀整段作废、重新冷启动一轮。** 这是唯一一个**完全在我们手里**的杠杆。

## 4. 三个杠杆的定价

### ② 缩 schema：**45.7% 的 schema 是两个参数逐字抄了 49 遍**（最大的一笔）

把 82,612 字符按"同名同内容的参数"聚一下，冒出来两个：

| 参数 | 单份 | 出现 | 冗余字符 | 占 schema |
|---|---|---|---|---|
| `intents` | 483 字符 | **50 条技能**（2 个文本变体） | **23,184** | 28.1% |
| `reply_kind` | 304 字符 | **49 条技能**（**1 个文本变体**） | **14,592** | 17.7% |
| | | | **37,776** | **45.7%** |

**`reply_kind` 的那份文本，一字不差地印了 49 遍。** user 角色同样：
18,681 字符里 **48.4%** 是这两格。

⚠️ **但"37,776 字符"里只有一半搬得动。** 单份参数对象 = **描述文本 + 结构**
（`items` 里那层 `{goal, workflow, params}` 的嵌套 schema 必须留着，拿掉模型就发不出合法实参）：

| 参数 | 单份对象 | 其中描述 | 其中结构 | 冗余(整份) | **冗余(只算描述)** |
|---|---|---|---|---|---|
| `intents` | 483 | 199 | 284 | 23,184 | **9,552** |
| `reply_kind` | 304 | 225 | 79 | 14,592 | **10,800** |
| | | | | 37,776 | **20,352** |

**能做的只有"把描述文本提到正文里写一次"**（约 424 字符 ≈ 232 tok），
结构原样留在 schema。**冗余 20,352 字符 = 24.6% 的 schema ≈ 9,688 tok / 次。**

| | 现在 | 去重后 |
|---|---|---|
| schema | 82,612 字符 → 39,319 tok | 62,260 字符 → 29,636 tok |
| 正文 | 23,477 字符 → 12,826 tok | 23,901 字符 → 13,050 tok |
| **合计** | **52,145 tok** | **42,686 tok（−18.1%）** |

> **更正（同日晚，第二次）**：本节初版写 **−33.7%**，那是按"整份参数对象都能搬走"
> 算的——**把 `items` 那层结构也算进了可省的部分**。真能做的是只搬描述文本，
> **−18.1%**。两次更正的方向都是"原来估高了"，所以下面 §4④ 那条新杠杆才是大头。

## 4④. 更大的一笔：把散文挪到 `describe_skill` 后面

上面的去重只动了**两格**。把整个 schema 剖开看：

| | 字符 | ≈tok | 占比 |
|---|---|---|---|
| 函数 `description`（含 `complete_when`） | 21,847 | 10,399 | 26.4% |
| 参数 `description` | 19,652 | 9,354 | 23.8% |
| **散文合计** | **41,499** | **19,754** | **50.2%** |
| 结构（名字/type/enum/required/嵌套 schema） | 41,113 | 19,570 | 49.8% |

**一半的 schema 是散文。** 而散文不是"签名"，是**一份内联的目录**——它描述的是
"这个站能干什么"，不是"这个函数怎么调"。

⇒ **修法**：结构全留（enum 白名单、工具名、required 一个字不动），散文挪到
一个 `describe_skill(name)` 后面；schema 里每条只留一句索引。

| | 现在 | 改后 |
|---|---|---|
| 结构 | 41,113 字符 → 19,570 tok | 19,570 tok（不动） |
| 散文 | 41,499 字符 → 19,754 tok | 索引 50×53 字符 ≈ 1,253 tok |
| 按需取 1–2 条 | — | ~500 tok |
| **schema 侧合计** | **39,319 tok** | **≈21,300 tok** |

**planner 输入 52,145 → ≈34,100 tok（−34.6%）。**

**为什么这不违反既有结论**：`saudade-agent-surface-carries-contract` 那条是
「删规划契约 ⇒ 检索族成片红 ⇒ 契约搬进函数 schema」——**但"搬进 schema" ≠ "必须常驻"**。
它要的是**决策那一刻看得见**，按需取正好满足。
**也不是 POC 那个"平铺 73 工具"**——那还是一份**完整**目录，只是更长；POC 证的是
"目录变长会崩"，没证"目录可以外置"。

⚠️ **代价与未验证处**（20261020 晚实测，见 §4④ 附）：索引质量决定短名单质量，
**而这一点用离线词法检索量不出来**（详见附注）；要定论得跑模型探针。


> ⚠️ **两条纪律**：
> 1. **只许去重，不许缩写。** 那 41,499 字符（schema 的 50.2%）的函数/参数描述里
>    装的是**路由契约**（"留言板与说说必须成对点名"、"执行属不属实不归本技能管"）——
>    工具菜单 POC 量到的正是丢掉这层翻译的代价（0.9825 → 0.6725）。
>    **去重是语义透明的；缩写不是。**
> 2. 描述换了位置 ⇒ 模型读到的**次序**变了 ⇒ **落地前要 golden A/B**，
>    判据是 POC 那三臂用的同一套（`landing_gate.ab_compare` + 19 条 regression 硬层）。

### ①③ 另两个杠杆

| 杠杆 | 收益 | 代价 / 约束 |
|---|---|---|
| **① 别再换模型**（或换完给它时间热） | 从 21%–61% 抬到 84.5% 那一档 | **零代码**。稳定性本身就是缓存策略 |
| **③ 重排 planner 提示词** | **≤1.3%**，真流量里更小 | 仍然值得做：它与 narrator 20261016 那次**同一类洞**，而且顺手补上 planner 缺的那把锁。**但不许记成省钱** |

**别做的事**：为了命中率去改 `round_info` 的**内容**（它是决策输入）、
为了命中率去按轮次裁菜单（前缀每轮都变 = 把现在那 42 次命中全打没）、
以及**在这三个杠杆之外**再造缓存机制。

## 5. 与工具菜单 POC 的关系

两条独立的线，**现在它们接上了**：POC 量的是准确率（`docs/tool-menu-poc-20261020.md`），
本篇量的是成本。POC 的结论是"**把 70 个工具平铺出去，准确率从 0.9825 掉到 0.6725**"，
原因是**丢掉了技能层做的那层意图→工具的翻译**；而 §4② 说 schema 里 45.7% 是抄了 49 遍的
同一个参数。**两件事指向同一个动作：动 schema 的"组织方式"，别动它的"内容"。**

- ❌ **平铺更多工具**（POC 已证伪，准确率崩）
- ❌ **缩写描述**（等于删翻译层，POC 已证伪）
- ✅ **去重**（本节 §4②，语义透明，−33.7% 输入）
- ✅ 真要"少而可组合"就得**手写分组**——那是第二轮，且**分组由谁写**要先回答（POC §5）

## 6. 复现（全部零 LLM 调用，唯一一次 4 次调用的探针见下）

```bash
# ① 命中率 / 双峰 / 按模型切（读生产 trace）
python - <<'PY'
import json, glob, collections
g = collections.defaultdict(lambda: [0, 0, 0])
for f in glob.glob("/home/ubuntu/Saudade-Blog/logs/agent/traces/**/*.json", recursive=True):
    d = json.load(open(f)); md = "?"
    for e in d.get("events") or []:
        if e.get("event") == "native_decision" and e.get("model"): md = e["model"]
        if e.get("event") == "llm_done" and e.get("node") == "planner":
            g[md][0] += 1; g[md][1] += e.get("input") or 0; g[md][2] += e.get("cache_read") or 0
for k, (n, i, c) in g.items(): print(k, n, f"{100*c/i:.1f}%")
PY

# ② 正文首个差异字节 / 52K 的构成：见本篇 §1–§2 的两段脚本
#    （渲染 _render_planner_prompt 两次做 diff；两角色两方程解 tok/字符）
```

**`x-opencode-session` 假设已被证伪**（`models/llm.py::_provider_headers` 每次调用发新 uuid）：
同一份 3,631 字符的 prompt 连发四次，第 3 次**换 session** 仍然命中
（`cache_read` 1920/2047，与同 session 的第 2 次逐字相同）⇒ **缓存不按 session 分桶**，
那行 uuid 不是成因、也不用改。**4 次调用，判据干净。**

## 附：§4④ 那条路，离线**验不了**（20261020 晚实测）

想用"词法检索能不能把正确技能排进 top-k"当代理，**失败了，如实记下来**——
失败本身有信息量，别让下一个人再走一遍。

**做法**：真值取生产 trace 的 `native_decision.workflow`（模型实际选中的技能）
＋该轮 `input.message`，得 **53 条真实配对**；query 取 `原话` 与 `原话 + recent_tail`
两档；同一套检索分别跑在**一句索引**与**完整 description**上，外加随机排序作反控。

| k | 索引(裸原话) | 完整描述(裸原话) | 索引(+tail) | 完整描述(+tail) | 随机 |
|---|---|---|---|---|---|
| 1 | 7.5% | 11.3% | 7.5% | 7.5% | 2.0% |
| 3 | 18.9% | 20.8% | 11.3% | 13.2% | 6.0% |
| 8 | 37.7% | 28.3% | 34.0% | 24.5% | 16.0% |

**两条读数，只有一条能用**：

1. ✅ **索引不比完整描述差**（k≥5 时甚至更好）⇒ **压缩成一句，对"能不能找到"几乎无损**。
   这是**同一检索器下的相对比较**，所以它站得住。
2. ❌ **绝对值太低（k=1 只有 7.5–11.3%，随机 2%）⇒ 这个代理量的是检索器，不是设计。**
   字符二元组对中文短句根本不行：`站上最新的文章有哪些？` 该 `content_query`，
   检索器给的是 `device_query / admin_notes / account_roster`。

**为什么这条路天生验不了**：生产里很大一部分轮次是**上下文依赖的追问**
（`看看吧` / `那第二条讲的是什么？` / `带我去吧`），**光看那句话谁都定不出技能**——
真 planner 是靠对话历史定的，而词法检索器读不出历史里的指代。
`recent_tail` 加进去反而更差（k=3 从 18.9% 掉到 11.3%），因为节选里混进了别的话题的词。

⇒ **要判 §4④ 成不成立，只能跑模型探针**（[eval/experiments/menu_shape_ab.py](https://github.com/BigLeopardCat/saudade-blog-agent/blob/563c8a5/eval/experiments/menu_shape_ab.py) 那条路，
50 条索引 × 若干用例），**离线词法代理做不到**。这也是本篇第二次"估高了"：
两次都是**把某个量算进了它不在的地方**（第一次把 `items` 结构算进可省、这次把
"能不能找到"算成词法问题）。
