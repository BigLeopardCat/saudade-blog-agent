# ADR-0002：未完成的意图由模型声明，完成由回执认定

- **状态**：已采纳（20260927，批 D）／**拨盘 20261007 关闭**——产线 `.env` 的
  `AGENT_TASK_STATE` 已由 `1` 改回 `0`（**机制与表都保留**，只关写侧拨盘）。
  依据与复核触发条件见文末《20261007 去留复核》。**20261008 本决策的"声明"那一半加了一个新
  出口**（每个技能上的 `intents` 字段，见文末《20261008 追记》）。**同日拨盘又被打开过一次**
  ——不是改 `.env`（仍写着 `0`），而是加了 systemd drop-in
  `/etc/systemd/system/saudade-agent.service.d/override.conf`（`Environment=AGENT_TASK_STATE=1`，
  20261008 18:35 落盘、20:29 重启生效）；回执 `/health` 的 `dials.agent_task_state=true`。
  ⇒ **`.env` 与 drop-in 这两个真值源现在不一致**，进程内取值以 drop-in 为准（**1**）。
- **背景文档**：`docs/native-toolcalls-mainline.md`（主线交接）、`docs/adr/adr-0001-*.md`
- **迁移**：`scripts/migration/agent_task_20260927.sql`（表 `agent_task`，已执行；头注含三端契约与 20260927 补记）
- **影响范围**：`agent/tasks.py`（新）、`agent/native_plan.py`、`agent/graph.py`、`server.py`、
  `config/settings.py`（`AGENT_TASK_STATE` 默认 off）、`src/routes/chat.rs`、`src/entity/agent_task.rs`

## 背景

agent 有两个"跨轮记不住"的缺口，形状完全不同，此前只补了一半：

- **已发生的事实**有系统载体：`execution_log`（checker 验收回执）。它的纪律是
  **不许模型自报**——回执由确定性执行器按 PASS 判定，模型说"我做完了"不算数。
- **未完成的意图没有载体**。剩余步骤只活在当轮 `state["plan"]` 里，那一轮结束即蒸发。
  现场故障：原话「带我过去后开启一个特效」，轮 0 导航完成后**直接 chat 收尾**，
  第二步从未被规划。批 B 的五档对照里，剩下的红**只剩这一族**（`multi_step` 4 条）。
  旁证：模型自己写过 `TODO: 开启特效`（提示词在教它写），而消费者只有 trace——
  **有写无读**。

## 决策

**分界线上移一格**：

| | 谁来定 | 载体 |
|---|---|---|
| 还剩什么没做完（意图） | **模型声明**（native 档的伪函数 `task_hold`） | 表 `agent_task` |
| 这一步做完了没有（事实） | **系统按执行回执**（producer 流尾确定性结算） | 同一张表的 `cursor`/`state` |

模型**没有**权限改 `cursor`/`state`：它只能提出声明，推进由回执决定。

## 依据（为什么意图不能让确定性扫描器产出）

判决性的一条：**扫描器看不见那个宾语**。`decisions.py::_scan_action_intents` 只认
**具名别名**（`_EFFECT_ALIASES` 里有"樱花/大雨"才扫得出 effect 意图），而这一族失败的
第二步恰恰是**未具名指称**（「开启一个特效」）——它没有任何可匹配的词形。要补就得把
"一个特效"这种说法穷举进词表，而那正是"每遇新词形必假红一次"的老路。

**"主人一共要几件事、还差哪一步"只存在于 planner 的决策里**，没有任何下游能推导出来。
所以这一格的信息来源只能是模型；系统能做的是**不信任它对完成度的自述**，只信回执。

## 落地形状（跨语言契约）

- 伪函数**两个**：登记 `task_hold`（`steps` `minItems: 1`）与撤下 `task_drop`（只有 `goal`）。
  两个都**不是技能**（`SKILLS` 里没有它们、`instantiate_plan` 不认），
  只在 native 档的 `tools` 数组末尾追加；`AGENT_TASK_STATE` 默认 off ⇒ schema 与消费方
  一起不存在，线上行为逐字节不变。
  **20260927 修订**：初版是**一个** `task_hold` 兼表两义（`steps` 留空 = 撤下，见下方"后果"
  里那条已作废的写法）。落地当天实测证明**一个形状担两种语义会串味**——模型把「这步我做完了、
  把这行收掉」也写成空 `steps`，narrator 于是对主人说"这件事已撤下不再跟踪"，
  而流尾结算又把同一行写成 `succeeded`（落库终态对、话不对）。拆开后空 `steps` 的
  `task_hold` 归**无效登记**（记一笔 `task_hold_invalid`，既不登记也不撤下），
  同轮两者并存 ⇒ **登记胜**（`task_drop_ignored`）。**拆形状仍不够**（4 次采样 3 次
  改用 `task_drop` 表达"我做完了"），故同批加第三道确定性判据 **完成 > 撤下**：
  `tasks.drop_is_completion()` 若发现撤下声明能被**本轮回执**结算成 `succeeded`，就不当撤下
  （判据与流尾结算同源，直接复用 `advance_by_receipts`；方向单一——零回执/查不到行一律放行撤下）。
  加闸后同一条多轮用例 flag-on 连跑 4/4。全量现场见 `docs/native-toolcalls-mainline.md` §6.9。
- 步骤 `tool` 的闭集 = 该身份**可见技能模板里的工具 ∪ 点名白名单**——与菜单同源，
  **不是**全量工具注册表（闭集里不许出现模型够不到的名字，否则这一步永远结算不掉）。
- 帧 `__TASK__`：Rust 在 JSON 文本解析**之前**拦下（与 `__EXEC__` 同族），
  **收到即落库、绝不转发前端**；载荷**不带身份两列**（`user_id`/`conversation_id` 由
  Rust 从请求取）⇒ 模型碰不到身份字段，这是结构性的。
- 读侧：Rust 取本会话未完结任务（终态过滤与上限 3 条都在 SQL 里，时效 72h 也只由这一端判）
  → `agent_tasks` → agent 渲染进 system 上下文。
- 结算：从当前游标**连续**推进、不跳跃；同轮新登记的行用声明时刻做下界
  （否则"先导航再登记"的那半步会被自己刚执行的回执立刻算完成）。

## 后果

**好的**：

- 那一族失败的第二步第一次有了载体：缺参数时**保留目标**并把要问的那句原样存下来，
  下一轮原样回放（`pending_question` 逐字复用，不由模型重编）——这与"追问一次就丢"是
  两种行为。
- **结算与 `execution_log` 同一条纪律**：模型说了不算，回执说了算。这一条比登记通道本身
  更难被绕过，因为推进的代码里没有任何一处读模型的话。
- 撤下**不需要新字段**：`task_drop` 只用同一个 `goal` ⇒ `cancelled`（**空间上仍不需要新列**，
  只是表达它的不再是"空 `steps` 的 `task_hold`"——那个写法已按上面"落地形状"里的
  20260927 修订作废）。幂等键**只按目标**（步骤不进键）正是为此——进键就会算出另一个键、
  长出第二行，而原来那行永远挂着，撤下也就撤不掉。

**代价 / 明确的局限**（如实记）：

- **结算判据是工具粒度、不看参数**：同一步骤声明的工具本轮被执行过就算推进——
  主人手动换了别的特效也会把该步算作完成。粗，但确定，且比"模型自称做完了"可信。
- **自由散文的多步声明不接**：本表的步骤必须带机器可读的 `tool`（结算按它对回执）。
  历史上存在一个只有散文、没有工具名的来源——文本档（`PLANNER_ENGINE=text`）的 `TODO:`
  行；把它接进来只会产出永远结算不掉的行。该档连同 `TODO:` 那份形态已于 **20261004 随
  接口层单通道化一起删除**（`PLANNER_ENGINE` 拨盘、文本兜底解析器全删，生产 384 份 trace
  里该兜底 0 次命中）⇒ 今天**没有**这条无工具名的来源了。**这条局限本身仍成立**：任何
  将来新增的、不带工具名的步骤来源都不许接进本表。
- 六态里 `submitted` / `failed` 当前**没有写入方**（登记只产 `running`/`input_required`，
  撤下产 `cancelled`，结算产 `succeeded`）；留着是因为它们是这张表语义的一部分，
  但别按"六态都被用到"去读这张表。
- 取消只有一条通道（模型显式调 `task_drop`），没有独立的取消入口；而这条通道至今**不由系统
  核实"主人到底说没说不做"**——刻意不做那层自然语言词表闸（误伤面大，同族前例
  `_freeze_policy_refusal` 不许扩）。唯一加上的确定性闸是**完成 > 撤下**（单向，
  见"落地形状"的 20260927 修订），它挡不住的一支已如实记在
  `docs/native-toolcalls-mainline.md` §6.9 的"残余"：同一个请求里**先撤下、后执行**时，
  闸看不到还没齐的回执。

**被否掉的备选**：

- *复用 `pending_action` 表*：两条可判定的理由——① 它被 `prepare_chat` 按
  `conversation_id + status='pending'` 读作"本会话最新一条跨轮待办"，任务行混进同一张表会
  让那段注入的判据**静默**变成"待确认动作或任务"；② 一次装的东西不同（那格装一个动作、
  分钟级、主人点头即关；这格装一串步骤、跨多轮、缺参挂着等）。生命周期与写入端都不同。
- *把 `TODO:` 行解析进本表*：见上"自由散文的多步声明不接"（该来源已随文本档删除，
  但判据不变）。
- *让模型自己维护进度*：那就是把已经修好的"自报事实"缺口重新打开一次。

## 20261007 去留复核（结论：**关**）

**问法**：在**原有基础上**（不新增用例、不换模型）——拨盘开着比关着好吗？

**四条互不依赖的证据**：

1. **产线零产出**。`logs/agent/traces/` 全量 **979 份**（20260906–20261006，唯一枚举入口
   `eval/trace_files.py`）：`planner.task_declare` **0 次**；`producer.task_inject` 331 次
   **全部 `n=0`**。只看开档窗口（≥20261003，57 份）：注入 57 次全 `n=0`、登记 0 次
   ⇒ **开了 5 天，这个功能一次都没被用过**（连"读"都没读到过一行）。
2. **语料结构上显示不出收益**。153 条 golden 里只有 1 条碰任务状态
   （`task_state_resume_settle`），而它的任务行是**夹具喂的** ⇒ 走的是**常开**的注入/结算侧，
   与拨盘无关（同用例轮 1 那条 `forbid_task_state` 负断言在关档下还会退化成空过）。
3. **A/B 两臂各两跑**（ABBA 序、全量 153 条、`GOLDEN_ADMIN_UID=721`/`GOLDEN_USER_UID=722`）：
   终红 OFF `{10, 5}`（均 7.5）vs ON `{13, 9}`（均 11）；首跑红 OFF `{10, 6}` vs ON `{15, 11}`。
   差异**不显著**（双比例 z≈1.19 / p≈0.23；首跑 z≈1.60 / p≈0.11，n=2 臂），红集交集
   OFF `{account_mute_popup, rag_project_files}` / ON 多 `account_unmute_popup`、
   `admin_write_question_no_exec`，逐条翻转形态与仓里已知噪声同形（同代码两跑 10 红 vs 3 红）
   ⇒ **判不了"有害"，但也没有任何一条红能由开档消掉**。
4. **开档的实际产出面**。四跑约 **615 轮**真链路里 ON 臂只产出 **2** 个任务侧事件：
   `task_declare` 1（`task_state_resume_settle` 轮 2，把夹具已注入的任务**重登记**一次）、
   `task_correct` 1（`admin_todo_done_popup` 轮 0 的**误登记**——无帧不落库，但多花一轮纠偏，
   且这是"声明→纠偏"这条本来就最容易出错的路径）；OFF 臂 0 次。
   成本侧：planner 的 `tools` schema **每次调用多 2,603 字符**（29,743→32,346，+8.8%）。

**结论**：**开档没有更好**——收益面 5 周 0 次命中，代价是每轮多 2.6k 字符 schema 与偶发误登记
（多一轮纠偏）；而"读→认→结算"链路**本来就常开**，关掉拨盘不会让任何已存在的任务行失去注入
或结算。**动作**：`AGENT_TASK_STATE=0`（一行 `.env`，可逆）。

**为什么先不拆机制**：关拨盘捕获了全部收益且可逆；拆机制要动
`agent/{tasks,native_plan,graph}.py`、`server.py`、Rust `src/routes/chat.rs` +
`src/entity/agent_task.rs` + 迁移 flag + 本 ADR + 若干测试，会把 §6.8/§6.9 已验过的形态
（含 `task_state_resume_settle` 用例与"完成 > 撤下"闸）一起拆掉。在下面那条触发条件出现前不值。

**复核触发条件**（满足任一：把拨盘打回 1，先跑 `eval/task_state_probe.py` 两档对照，
再按 §6.8 的两轮探针复测）：

1. 生产模型 / provider 换代（今天 `qwen3.8-flash`）——换档后"模型愿不愿意登记"要重新问一次；
2. 产线 trace 里第一次出现**真实的**多步未完成意图证据（如"先带我过去、然后…"而第二步从未被
   规划，即本 ADR《背景》那族的现场故障形状）；
3. 任一真链路窗口里 `planner.task_declare` 自发登记 **>0** 次。

## 20261008 追记（批 ②：模型列全部意图 + 声明侧的第二个出口）

**这不是去留复核，是决策本身的一次修订**——不动"剩什么由模型声明 / 做完没由回执认定"这条
分界，只给**声明**这一侧补一个出口。**本文的读数全部在命令行 `AGENT_TASK_STATE=1` 下取得**
（`GOLDEN_ARM=matrix`，离线 harness，不经过产线进程）。

**拨盘状态（与上一条《20261007 去留复核》的"关"不同）**：20261008 18:35 起本机多了 systemd
drop-in `.../saudade-agent.service.d/override.conf`（`Environment=AGENT_TASK_STATE=1`），20:29
重启生效 ⇒ **进程内是开的**（`/health` `dials.agent_task_state=true`），而 `.env` 仍写着 `0`。
**两个真值源不一致这件事本身挂着待拍板**（把 drop-in 删掉回退，或把 `.env` 改成 1 让两处同源），
**不是本追记能裁的**。另一个必须一起读的事实：**产线生效的是工作区**——上一次重启（20:29:43）
早于本追记所记代码的落盘时间（22:09–22:25）⇒ **新出口此刻并未在产线上跑**，要它生效得再重启。

**动机（一线故障形状）**：《背景》那一族的现场是「带我过去后开启一个特效」而第二步从未被规划。
20261007 的复核结论是"先关拨盘、机制留"，理由之一是**模型不主动登记**。批 ② 换了个问法：不
指望模型在为某个技能做决策时顺手登记，而是**一次把这一句主人话里要做的事全列出来**，系统减去
本轮已办的、把剩下的确定性登记（`tasks.intents_to_declarations`，steps 由该技能的 `plan` 模板
推）——登记因此不再依赖"模型觉得有必要登记"。

**什么变了**：

1. **第三个伪函数 `task_intents`**（清单的出口一）：形状 `[{goal, skill}]`，`goal` 空白丢、
   `skill` 不在 `visible_skills(role)` 里或为 `chat` 丢（推不出步骤）、超 `TASK_MAX_INTENTS`
   截断——逐项判、**单项丢而不整份作废**（清单的价值在"别漏"，为一件写坏的丢掉整份，换来的正是
   要治的病）。模型只交清单的那一轮零动作，由 `_INTENTS_ONLY_NUDGE` 纠偏一次。
2. **声明侧的第二个出口：每个技能函数多一格可选 `intents`**（`tasks.INTENTS_ARG`）。它存在的
   理由是**结构性的**：native 档 `parallel_tool_calls=False` ⇒ 一轮只能发一条调用 ⇒「交清单」
   与「点技能」在同一轮里**互斥**。两条互为否定的真跑证明了这不是方差：同一句 prompt、同一份
   schema、`temp=0.0`，一次交清单（当轮零动作）、一次直接点技能（剩下的那件没人记）。
   `native_plan.tool_calls_to_plan` 把它从 args 里 `pop` 掉 ⇒ 不进 `params`、不进 TOOLS 行。
3. **三条排除规则**（与判据侧 `require_task_goal_per_intent` 同源）：`skill ∈ acted_skills`、
   模板工具全在回执里、`goal ∈ skip_goals` ⇒ 本轮真办掉的那件自动出局。**"多填无害"是判据保证
   的**，所以字段描述敢写"含你这一轮正要办的那件"。

**本 ADR 的两条不变量未动**：模型仍然**没有**写 `cursor`/`state` 的通道（推进只由
`advance_by_receipts` 按回执发生）；意图仍然**只由模型声明**产出——新出口改的是形状，不是权威。

**读数与成本**：`GOLDEN_ARM=matrix` 两条靶连跑三次 **6/6 通过**（此前 0/2），5 次走新字段通道、
1 次"先列后办 + 纠偏"，`resets` 全 0。代价：planner `tools` JSON 30241 → 51302 字符
（≈ **+7.6k 输入 tokens / 次 planner 调用**，仅开档时；重复轮几乎全吃 cache）。完整版见
`docs/native-toolcalls-mainline.md` §6.11。

**两条如实记下的边界**：① inline 通道下**上卡的那件不建任务行**（卡是它的载体），卡被取消/过期
时那件没有 `agent_task` 兜底——判据侧本来就按 `state="cancelled"` 不算登记，**未额外补行**；
② sink 是 `task_sink[:] = frames` **覆盖语义**，第二次决策若只列剩下那几件，最终登记是上一版的
**子集**。

**对上面《复核触发条件》的影响**：第 2 条（出现真实的多步未完成意图证据）**多了一个前置动
作**——先按本追记的新出口在开档下复测；第 1、3 条字面不变。**本追记不作为"打开拨盘"的依据**：
6/6 是开档下的真链路读数，不是 OFF/ON 对照（后者仍是 20261007 那份四跑 A/B，红集交集为空 ⇒
不可判读）。

## 20261009 追记（批 ② 续：清单的两个失败方向各堵一处 + 声明侧的出处对账）

**仍然不是去留复核。** 批 ② 造出了"模型一次列全这一句话里的事"这条通道，本追记补的是这条
通道自己的两个**互斥**失败方向，外加**目标文本的出处**。分界一字未动：登记仍然只由模型声明产
出，完成仍然只认回执（`advance_by_receipts`），模型仍然**没有**写 `cursor`/`state` 的通道。

**拨盘**：真值源仍是 `.env` 一处（drop-in 20261008 22:45 已退役）。本批改的是"点了技能那一
轮"，与 schema 档位无关 ⇒ 离线套件在 `AGENT_TASK_STATE=0` 与 `1` 两档**各跑一遍，红套件数都是
0**（`tests/run_all.py` 110/110；`run_all.py` 那把钉子把档位钉成 0，所以第二档必须手工单跑一遍
——"离线套件对档位是瞎的"这条纪律照旧）。

**追记一：目标里的号必须有出处**（`tasks.reconcile_goal`，`sources` 贯穿 `intent_frames` →
`intents_to_declarations`）

- **现场**：golden `mix2_two_writes_one_breath_card_only`（「想建个新分类叫「临江仙」，文章 23
  的标签也想换成「Rust」」）改前 **0/3**。读 trace 分不出是哪一种坏——`frames: 0` 有三种成因
  （会话 id 不是整数、推不出步骤、**目标本身被丢弃**），而 `goal` 文本**根本不在 trace 里**。
- **规则**：`goal` 里的数字（`\d+`）必须全部在 `sources` 里出现过。对不上 ⇒ **退回主人原话里
  最接近的那一段**（按骨架相似度 `_GOAL_MATCH_MIN=0.5`，骨架里数字整体换成 `#`、抹掉引号与空
  白——要判的正是"号对不对"，把号留在骨架里会让「文章 2」与「文章 23」看着不像同一件事）；
  一份来源里一段都够不着 ⇒ **这一件不登记**（`goal_dropped`），因为那个号下一轮会被 planner
  当成主人的原话读回来。
- **只认数字，不认命名实体**：名字对不对是自然语言问题（同义词/简称/省略），拿词表去判正是
  "每遇新词形必假红"的老路；而数字是 `goal` 里唯一机器可判的部分，也恰好就是出错的那几个字。
- **出处只取主人的话**（`graph._task_goal_sources`，最近 4 轮、`[System: …]` 注入与 AI 回复不
  算）。这是**刻意比另外两族窄**：《写参数的出处分两族》里"站内台账里的值也算出处"，因为那边的
  参数值本来就来自台账；这里登记的是**目标文本**，台账里那一行正是从这份文本渲染出来的，拿它
  当出处等于自我印证。
- **跨轮复述是合法重提**：出处取**所有**来源的并集，不是只看本轮那一句——主人上一轮说过的 id，
  模型从执行记忆里取回来复述，是本 ADR 一直承认的合法形态。
- **排在三条排除规则之后**（其中一条因此要判两次）：被前三条例外的件本来就不登记，先对账只会往
  读数里灌噪声；而**改写之后**的文本可能与显式登记过的那件同目标（幂等键按 goal 指纹算）⇒ 改
  写后必须再判一次 `same_goal`，否则会长出两行同义的未完成。

**追记二：反方向补交**（`_INTENTS_BACKFILL_NUDGE` + `_multi_item_shape`，`graph.py`）

- 批 ② 的两个出口在 native 档**互斥**（`parallel_tool_calls=False`，一轮只发得出一条调用）。
  ③ 治"只列不办"（交清单、零动作），④ 治它的反方向：**点了技能、清单却没留下要记的** ⇒ 没上
  卡的那件从登记里彻底消失。手法与 ③ 同一个：不是再劝一次，而是把清单那条伪函数从 schema 里
  **摘掉**（`deny_pseudo`），剩下的出口正好长在模型已经选中的那个技能的参数里——不用改主意、
  不用多点一次工具。**判据是"减完还剩几件"，不是"清单是不是空的"**：第一版写成
  `not decided.intents`，当夜的同批复核当场抓到它漏掉另一半——同一句话的另一跑
  （trace `20261009_032513`）清单**非空**，但里面只写着"这一轮正要办的那件"，被排除规则减完
  一件不剩，`listed=1 / acted=['category_create'] / frames=0`，另一件照样消失。改成
  `_intents_left_count(...) == 0`（用**真登记那条路的同一个函数** `tasks.intent_frames` 数），
  两种形状就成了一个信号；两条同义说明（"系统减完就一件不剩"）也一并写进纠偏语——对着一份非空
  的清单说"你没交清单"是**假话**，模型多半会去证明自己交过。
- **只在形态像多件事时才多花这一轮**：`_multi_item_shape` = 有多个子句，且**非首句**里出现多字
  连接词。形态判据故意偏召回（误判的代价是白花一轮：模型照旧点它本来就要点的那个技能，多填一格无
  害）；**单字 `和/与/跟/及` 刻意不收**——收的那一版当场在 `tests/test_todo_schedule.py` 的端到端
  上误伤：生产原话「…探讨引入 JEV 等决策模式的**修改面和**后续评估升级。2.…」里那个 `和` 长在
  待办正文的**名词短语**里，于是"一条带编号的待办"被判成两件、白催一轮（那一支的 LLM 轮次是计
  数进判据的，测试当场红）。

**那 4/17 的红逐条定过性**（如实记，`raw_*` 那两格就是为这一步加的）：

- **两跑同一种形状：模型写的目标里一个号都没带**——`{listed: 2, frames: 1, acted:
  ['category_create'], retraced: 0, dropped: 0, goals: ['给文章打标签']}`。`reconcile_goal` 对
  "没有数字"的 goal 是**放行**（没有可对账的东西），判据侧 `require_task_goal_per_intent` 要求目标
  含「文章 23」⇒ 它红得对：模型把目标**概括**掉了。**修它要动的是"目标要不要逐字抄主人原话"的契约，
  不是这条对账**——留给下一批（这一族对账看不见，理由见下面第三条边界）。
- **一跑是上面那个"清单只写了正要办的那件"**（`listed=1 / acted=['category_create'] / frames=0`）
  ⇒ **已被本追记的第四格修掉**（判据从"清单空不空"改成"减完还剩几件"）。
- **一跑是 ④ 管不着的另一族**：`listed=2, frames=1, acted=[]`，模型选了 `chat` 交了清单、**一张卡
  都没弹**（判据的红是「本轮没有发出 `__CONFIRM__:` 帧」）。那属于 ③ 那一格（只列不办），纠偏一次
  之后仍然没动作——**不是登记这一半的事**。

**①的当场收获（这条是意外证据，比读数更值钱）**：同一批里有一跑的 `raw_dropped` 是
**「给文章 103 添加标签「随笔」」**，下一批又抓到 **「给文章 123 增加标签「随笔」」**——主人说的是
「文章 23」，标签说的是「Rust」，**号与值两个都是编的**。改前这一件会**带着假号登记进台账**，下一
轮 planner 把那一行当"主人说过的事"读回来（正是《写参数的出处分两族》乙族那条教训的登记版）。现在
它被挡在登记之外。**顺带一条如实记的不足**：那一跑的 goal 与主人原话那一小段的骨架相似度是
**0.417**，够不到 `_GOAL_MATCH_MIN=0.5` ⇒ 没走"退回主人原话"那条更好的出口，而是**丢弃**了。一条
样本不动阈值（`_GOAL_MATCH_MIN` 的注释本来就写着"定得松是刻意的、判错的最坏结果是落到相邻那一
段"）——**要动它得先有一批样本，不是拿一条读数反推阈值**。

**④ 扩形状后的第一次真链路复核（同夜，6 跑）**：**4/6 通过**。扩形状当场生效——有一跑的
`planner.intents_backfill` 是 `listed=2`（旧版在这里判不出来），纠偏后重决策。两跑红**不是** ④
的事，指向同一个机制事实：

| 那两跑的 `task_auto`（**同一轮的两条事件**） | |
|---|---|
| 第 1 条 | `round=0 listed=2 frames=2 acted=[]`，goals = `['新建一个文章分类叫「临江仙」', '把文章23的标签改成「rust」']` |
| 第 2 条 | `round=0 listed=2 frames=1 acted=['category_create']`，goals = `['新建一个标签叫「Rust」']` |

判据看到的是**第 2 条**——`task_sink[:] = frames` 是**覆盖语义**（§6.11 第三条边界），而后一次的
清单是模型"已经办了第一件、回头再说第二件"时的**重述**，重述里把「文章 23」这个号**概括掉了**
（`reconcile_goal` 对没有数字的 goal 是放行，见第三条边界）。⇒ **一次本来就对的登记被后一次的坏
重述覆盖**，两跑都红在同一格（「没上卡的那件事没有留下任务登记：期望有一帧 `__TASK__` 的 goal 含
'文章 23'」）。**这不是本追记引入的**（§6.11 已把覆盖语义记为边界），但它今晚第一次有了"覆盖把绿的
变成红的"的现场。**处置留给下一批**：可选的口径有"首次非空优先、后续只补本回合没登记过的技能"
（保登记完整、代价是可能丢一次更准的重述）与"并集 + `same_goal` 去重"（保两次都留、代价是同一件事
可能长两行）——**两个方向各有代价，属于决策不属修 bug，不在本夜擅动**。

**成本（如实记）**：④ 只在"形态像多件事 **且** 模型点了真技能 **且** 减完一件不剩"时触发。可触发的
上限：golden 186 条 / 178 轮里形态命中 **15 轮（8.4%）**；生产 trace（20261006 起 102 份）形态命中
**5 份**，其中 3 份是「确认执行：…」那种**确认令牌轮**（按令牌实例化计划、不调 LLM）⇒ 真正可能多花
一次 planner 调用的约 **2/102**（上限算在形态这一层，两个形状都是它的子集）。上线后这一格的 trace
计数是 `planner.intents_backfill`，带 `listed`（0 = 没交，>0 = 交了但只剩它正要办的那件）。

**三条诚实边界**（与 `_multi_item_shape` 长注同一份，别读成覆盖率）

- `A 和 B` 挤在同一个子句里读不出来（单字连接词收不得，见上）；整句**没有子句分隔符**的多件事
  （「带我过去后开启一个特效」）也读不出来；`A、B` 顿号并列**不算两件事**（切了会把「文章 23、
  19 的标签」同一个宾语的两个值读成两个目标）。三条都是"读不出来"，不是"判错了"。
- 形态命中里含**假阳性**（golden 那 15 轮里有「泠月喵你真的好可爱呀！…」这类纯表扬句）。代价有界
  ——最多一轮纠偏，且 ④ 还要求模型真的点了技能且没交清单。
- **出处对账只覆盖数字**：命名实体（分类名、账号名、标题）写错了这条闸看不见。判据侧那条
  `require_task_goal_per_intent` 也只查数字——两处一致是刻意的，别单方面加宽一边。

**trace 读数新增**：`planner.task_auto` 加 `retraced` / `dropped` 两个计数与 `raw_retraced` /
`raw_dropped` 两条**改写/丢弃前的 goal 原文**（截 60 字、各最多 3 条）。理由与 `conv` 那个字段同一
条：只有计数时"`dropped: 1`"有两种相反的读法——"模型编了一个号，拦得对"与"模型写的是对的，是这
道闸过火了"——而 trace 里看不出是哪一种。原文一进 trace，下一次读的人一眼分得开。

**对上面《复核触发条件》的影响**：三条字面不变。本追记**不作为"打开拨盘"的依据**——上面的读数是
"同一档下改前改后"，不是 OFF/ON 对照。`AGENT_TASK_STATE=0|1` 的两臂全量对照（只读红集交集与
`planner.task_declare` / `producer.task_inject` 的计数）仍待跑。
