# ADR-0002：未完成的意图由模型声明，完成由回执认定

- **状态**：已采纳（20260927，批 D）
- **背景文档**：`docs/native-toolcalls-mainline.md`（主线交接）、`docs/adr/adr-0001-*.md`
- **迁移**：`scripts/migration/agent_task_20260927.sql`（表 `agent_task`，已执行；头注含三端契约与 20260927 补记）
- **影响范围**：`agent/tasks.py`（新）、`agent/native_plan.py`、`agent/graph.py`、`server.py`、
  `config/settings.py`（`AGENT_TASK_STATE` 默认 off）、`src/routes/chat.rs`、`src/entity/agent_task.rs`

## 背景

agent 有两个"跨轮记不住"的缺口，形状完全不同，此前只补了一半：

- **已发生的事实**有系统载体：`execution_log`（checker 验收回执）。它的纪律是
  **不许模型自报**——回执由确定性执行器按 PASS 判定，模型说"我做完了"不算数。
- **未完成的意图没有载体**。剩余步骤只活在当轮 `state["plan"]` 里，那一轮结束即蒸发。
  现场故障：原话「带我过去后开启一个特效」，轮 0 导航完成后**直接 chat 收尾**，
  第二步从未被规划。批 B 的五档对照里，剩下的红**只剩这一族**（`multi_step` 4 条）。
  旁证：模型自己写过 `TODO: 开启特效`（提示词在教它写），而消费者只有 trace——
  **有写无读**。

## 决策

**分界线上移一格**：

| | 谁来定 | 载体 |
|---|---|---|
| 还剩什么没做完（意图） | **模型声明**（native 档的伪函数 `task_hold`） | 表 `agent_task` |
| 这一步做完了没有（事实） | **系统按执行回执**（producer 流尾确定性结算） | 同一张表的 `cursor`/`state` |

模型**没有**权限改 `cursor`/`state`：它只能提出声明，推进由回执决定。

## 依据（为什么意图不能让确定性扫描器产出）

判决性的一条：**扫描器看不见那个宾语**。`decisions.py::_scan_action_intents` 只认
**具名别名**（`_EFFECT_ALIASES` 里有"樱花/大雨"才扫得出 effect 意图），而这一族失败的
第二步恰恰是**未具名指称**（「开启一个特效」）——它没有任何可匹配的词形。要补就得把
"一个特效"这种说法穷举进词表，而那正是"每遇新词形必假红一次"的老路。

**"主人一共要几件事、还差哪一步"只存在于 planner 的决策里**，没有任何下游能推导出来。
所以这一格的信息来源只能是模型；系统能做的是**不信任它对完成度的自述**，只信回执。

## 落地形状（跨语言契约）

- 伪函数名 `task_hold`：**不是技能**（`SKILLS` 里没有它、`instantiate_plan` 不认它），
  只在 native 档的 `tools` 数组末尾追加；`AGENT_TASK_STATE` 默认 off ⇒ schema 与消费方
  一起不存在，线上行为逐字节不变。
- 步骤 `tool` 的闭集 = 该身份**可见技能模板里的工具 ∪ 点名白名单**——与菜单同源，
  **不是**全量工具注册表（闭集里不许出现模型够不到的名字，否则这一步永远结算不掉）。
- 帧 `__TASK__`：Rust 在 JSON 文本解析**之前**拦下（与 `__EXEC__` 同族），
  **收到即落库、绝不转发前端**；载荷**不带身份两列**（`user_id`/`conversation_id` 由
  Rust 从请求取）⇒ 模型碰不到身份字段，这是结构性的。
- 读侧：Rust 取本会话未完结任务（终态过滤与上限 3 条都在 SQL 里，时效 72h 也只由这一端判）
  → `agent_tasks` → agent 渲染进 system 上下文。
- 结算：从当前游标**连续**推进、不跳跃；同轮新登记的行用声明时刻做下界
  （否则"先导航再登记"的那半步会被自己刚执行的回执立刻算完成）。

## 后果

**好的**：

- 那一族失败的第二步第一次有了载体：缺参数时**保留目标**并把要问的那句原样存下来，
  下一轮原样回放（`pending_question` 逐字复用，不由模型重编）——这与"追问一次就丢"是
  两种行为。
- **结算与 `execution_log` 同一条纪律**：模型说了不算，回执说了算。这一条比登记通道本身
  更难被绕过，因为推进的代码里没有任何一处读模型的话。
- 撤下**不需要新字段**：用同一个 `goal`、`steps` 留空再登记一次 ⇒ `cancelled`。
  幂等键**只按目标**（步骤不进键）正是为此——进键就会算出另一个键、长出第二行，
  而原来那行永远挂着。

**代价 / 明确的局限**（如实记）：

- **结算判据是工具粒度、不看参数**：同一步骤声明的工具本轮被执行过就算推进——
  主人手动换了别的特效也会把该步算作完成。粗，但确定，且比"模型自称做完了"可信。
- **文本档不接**：`PLANNER_ENGINE=text` 的 `TODO:` 行没有机器可读的步骤工具，接进来只会
  产出永远结算不掉的行。归档分支上的形态**不会被本表救**。
- 六态里 `submitted` / `failed` 当前**没有写入方**（登记只产 `running`/`input_required`，
  撤下产 `cancelled`，结算产 `succeeded`）；留着是因为它们是这张表语义的一部分，
  但别按"六态都被用到"去读这张表。
- 取消只有一条通道（模型在同一 `goal` 上重新声明），没有独立的取消入口。

**被否掉的备选**：

- *复用 `pending_action` 表*：两条可判定的理由——① 它被 `prepare_chat` 按
  `conversation_id + status='pending'` 读作"本会话最新一条跨轮待办"，任务行混进同一张表会
  让那段注入的判据**静默**变成"待确认动作或任务"；② 一次装的东西不同（那格装一个动作、
  分钟级、主人点头即关；这格装一串步骤、跨多轮、缺参挂着等）。生命周期与写入端都不同。
- *把 `TODO:` 行解析进本表*：见上"文本档不接"。
- *让模型自己维护进度*：那就是把已经修好的"自报事实"缺口重新打开一次。
