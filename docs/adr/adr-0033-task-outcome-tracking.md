# ADR-0033：按需任务清单与准备工具的暂停契约

- **状态**：已采纳，真实任务验收分批推进。
- **影响范围**：博客能力装配、标准任务清单、模型工具说明与复合任务评测。

## 决策

复杂任务可通过 `task_planning` 领域加载 LangChain `TodoListMiddleware` 的标准
`write_todos`。工具、状态 schema、重复更新检查与 Command 都复用框架实现。
业务 harness 不解释清单执行步骤，不新增规划模型、意图路由或计划 DSL。
清单只有简短的事项和状态；所需证据编号写在事项内容中，不保存长推理。

标准清单状态由 Agent 子图 checkpoint 持有。审批与恢复保留同一任务的清单，
新任务重置清单。简单对话不加载工具、不注入清单说明，也不强制调用模型规划。
清单完成状态不授予写权限，不作为任务成功证据。审批前交付回复时不注入更新清单的工具指令，
避免要求模型更新清单、同时又以 tool_choice 禁止调用的冲突。

执行与交付指令放在 system 指令正文中；角色、权限、渲染能力等事实保留为 JSON 数据。
准备工具返回后，同一 Agent 以标准 `tool_choice=none` 生成交付回复，再提交轮次并等待审批。
保持已加载工具 schema 不变，避免仅因禁止调用而重新排列缓存前缀；服务端也拒绝在该阶段执行新调用。
该轮可以交付已有读取证据支持的总结，不授予写权限，不重复卡片元数据。
空回复最多重试一次，仍共享任务预算与截止时间；失败保留有来源的准备状态，不编造答复。
确认后在等待回复之后追加新的执行事实，模型据此继续剩余事项。
这会为每张卡增加一轮同模型调用；没有独立叙述模型、旁路状态或新增调度循环。

默认任务上限为 64K token、12 次模型调用和 16 次工具尝试，含缓存输入、工具发现、
审批前答复、恢复及摘要，均累计持久保存；上下文窗口仍为 16K，实际请求有独立截止时间。
原 32K/8/8 会截断正常改卡与带清单的多步任务，调整不取消硬上限或未知写入保护。

## 验收边界

总结未读、固定确认范围、实际已读效果、后续导航与旧授权回放分开检查。
没有总结正文，即使弹卡且零写入也判失败。执行期间新到通知不包含在原确认中。
HTTP 浏览器回执与框架恢复沿用 P0 测试；模型夹具中的导航命令不等同于浏览器页面已完成渲染。

任务清单只能帮助模型跟踪事项，不能保证语义完整性。真实模型重复评测、事实范围检查、
部分失败和多义目标仍按 [任务可靠性计划](../task-reliability-plan.md) P1 验收。
