# ADR-0005：多模态检索方向认可，但**现在不做**——等图片规模与查询形态

- **状态**：已搁置（20261005）——**方向认可，条件未到**，重开条件见下
- **背景文档**：[../multimodal-retrieval.md](../multimodal-retrieval.md)（分阶段方案与判据）、
  [../rag-design.md](../rag-design.md) §8（检索侧的触发条件驱动升级预案）
- **影响范围**：无。本次一个字都没改代码——这份 ADR 存在的目的就是**别再重开一遍讨论**
- **触发条件**（**两条同时满足**才重开；在此之前"图片检索"的正确形态是文字）：
  1. 站内图片数量 **≥ 1000 张**（今天 19 张）；
  2. 出现**没有文字可概括**的查询——即用户拿着一张图问"有没有跟这张像的"，
     或者搜"那个蓝色的、有山的图"。只要查询能写成文字（"夜景"、"架构图"），
     走文字检索就够，**用不着联合嵌入空间**。
- **判据**：无（没改代码）。重开时第一件要建的是判据，见
  [../multimodal-retrieval.md](../multimodal-retrieval.md) 的《判据》一节

## 背景

### 现状①：「对话里看图」已经能用，缺的从来不是这一块

`server.py` 从 20260828 起就把用户上传的图拼成 OpenAI `image_url` 内容块送进模型
（多图 ≤6 张、单图 ≤1.6M 字符 base64；图片块拼在消息**尾部**，前缀零污染、不吃缓存）。
也就是说**模型确实看得到图**——今天问它"这张图里是什么"，它答得出来。

真正没有图的地方是另外两处，而且两处都不是"没接上"，是**按设计**：

- **确定性层看不见图**：`agent/context.py::_msg_text` 只取 content 数组里的 `text` 块。
  意图分类、指代锚点、重复调用拦截这一族纯函数消费的是文本，塞进 base64 只会让
  `content[-500:]` 截到图片垃圾。这是对的，不该改。
- **检索层看不见图**：`rag/search.py` 的 BM25 与向量路吃的是**文本**。图片没有 caption
  字段、没有任何文字表征 ⇒ 对检索而言图片**根本不存在**。这才是缺口本体。

### 现状②：图片不进对话历史

Rust 侧落库时图片被换成 `[图片]` / `[图片×N]` 标记，图片本体不入 `chat_history`。
所以跨轮的"那张图"**没有数据源**：下一轮模型只知道"上一轮有过一张图"，
看不到图本身、也没有 id 可以引用。这与"检索看不见图"是两件事，
但都指向同一个前置件——**图片需要一个文字化的身份**。

### 现状③：规模量不出任何东西

站内图片 19 张。这个数字意味着：任何"换了检索方式有没有变好"的结论都**测不出来**——
同族教训就在 22 条 query 的 L1 上（当时的结论只能是"没变差"，读不出单一用例的涨跌，
见 [../eval-observability.md](../eval-observability.md)）。19 张图上做联合嵌入空间，
结果是搭起一整套基建、然后没有任何办法判断它有没有用。

### 现状④：本机跑不了本地视觉模型

生产机可用内存约 1.5GB、swap 已近耗尽（3979/4035MB）⇒ 本地留 CLIP/BLIP 这类模型
没有可行性。任何重排/打标都得走远端 API，走 API 就得算钱、算超时、算限流，
这些都只有在规模真的到了的时候才划算。

## 决策

**现在不做多模态检索。** 理由不是"做不到"，是**收益不可测量**：

- 19 张图的语料上，一个图像检索器与"什么都不做"的差别落在噪声里；
- 前置件（caption）没做之前，做联合嵌入是**在错的路上加速**——
  没有文字表征时，检索框里的"这张图相关吗"连评测集都造不出来；
- 本仓的历史纪律是"先有判据再动代码"，而这一块的判据需要规模才立得住。

取而代之，**把方案写下来、把触发条件写成可观测的数字**，然后挂一个 `future` 标签的
issue 保持开着（[../adr/README.md](README.md) 的状态取值表：搁置 = 迟早要做、等一个信号）。

### 当时的替代选项，以及为什么不选

| 选项 | 否决理由 |
|---|---|
| 直接上联合嵌入空间（图/文映射到同一向量空间） | 19 张图 + 没有 caption ⇒ 造不出评测集，"变好了"无法证伪。且它跳过了一个必要前置：**图片先得有文字** |
| 先做本地视觉模型给图打标 | 本机内存/swap 不够（现状④），且打标质量不可控时，错标会以"检索命中一个不相关的东西"的形式静默传播 |
| 先做"以图搜图"（相似图） | 这正是触发条件②描述的场景——**等它真的出现再做**，今天没有任何人在用这个功能 |
| 干脆不写、不留痕 | 被本仓反复验证过的最贵选项：代码里看不见"一个没写出来的功能"，于是每隔一阵子重新讨论一次，每次都要把上面这些事实重新查一遍 |

### 重开时的第一步（**不是**接模型）

按 [../multimodal-retrieval.md](../multimodal-retrieval.md) 的分期：**第 0 期是 caption**，
即图片入库时（或补跑一次）生成一段文字描述、落成字段。原因在这一份 ADR 里已经写了三遍：
检索吃文本、确定性层吃文本、跨轮指代需要文本。caption 一旦就位，
**现有的 BM25 与向量路一行不改就能检索图片**——那才是投入产出比最高的那一格，
而它今天缺的不是技术，是"图片还不够多到值得为它建一条链路"。

## 复验

重开这份 ADR 时，先复核下面四个数（它们会随站点自然变化，ADR 里的取值是 20261005 的）：

| 事实 | 20261005 取值 | 怎么量 |
|---|---|---|
| 站内图片数 | 19 | 上传目录计数 |
| 图片是否有文字字段 | 没有 | `note`/`talk` 等表的图片字段只有 URL/缩放 |
| 图片能否进对话历史 | 不能（只存 `[图片×N]`） | `chat.rs` 落库处的替换 |
| 本机可用内存 / swap | ~1.5GB / 3979 of 4035MB | `free -m` |
