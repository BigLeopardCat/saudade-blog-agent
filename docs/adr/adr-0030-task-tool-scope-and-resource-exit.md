# ADR-0030：任务内工具激活与明确资源终止

- **状态**：已采纳；生产验收另行记录，不代表全项目迁移验收完成。
- **范围**：工具生命周期、硬预算停止、框架与业务责任边界。

## 采用的成熟接口

模型与工具循环使用 LangChain `create_agent`，状态 reducer、checkpoint、interrupt 和恢复由 LangGraph 管理。动态工具通过标准 `ModelRequest.override(tools=...)` 接入；摘要使用标准 `SummarizationMiddleware`。这些能力不再由应用另建执行循环。

参考官方 [上下文工程](https://docs.langchain.com/oss/python/langchain/context-engineering)、[内置中间件](https://docs.langchain.com/oss/python/langchain/middleware/built-in)和[人工确认](https://docs.langchain.com/oss/python/langchain/human-in-the-loop)，并核对锁定版本 LangChain 1.4.6 的源码。内置调用限制到达边界后结束或报错，不需要再调用模型编造业务收尾。

## 决策

- 已加载工具只属于当前框架任务。新任务不继承上个任务的完整领域定义；会话记忆仍保留。删除会话级激活镜像、可淘汰集合和淘汰策略，避免维护第二套工具缓存。
- 当前任务的暂停、确认和浏览器等待继续使用原 checkpoint 的工具与消息；恢复不等于新任务。现有来源、权限、签名和独立执行账检查继续有效。
- 硬预算不足时明确终止并记录 `blocked` 和实际原因，保留已提交事实和回执。不卸载全部工具、追加收尾提示、改变输出预算再付费调用一次模型；预算失败不能显示成正常完成。
- 应用只保留宿主验签、工具授权、签名确认、独立幂等执行账，以及跨 HTTP 接续累计 token 的持久记账。这些是当前产品所需边界，不能用仅按单次调用计数的中间件假装替代。

## 没有直接采用的组件

`ProviderToolSearchMiddleware` 在当前锁定版本只支持 OpenAI 和 Anthropic 的服务端工具搜索，不支持当前 DeepSeek 端点。不能因客户端兼容 OpenAI 请求格式而推定服务端具备该能力。

`LLMToolSelectorMiddleware` 会在模型调用前增加结构化选择调用；当前源码只传最后一条用户消息。隔离探针中，“先看看就好”丢失前文未读通知语境后选成了站点介绍工具。这个小样本不证明该组件普遍无效，但足以阻止直接替换当前多轮产品。后续若采用，必须先验证完整上下文、额外调用和总任务成本，不能只比较主模型的工具数量。

已有签名确认需要绑定真实目标、权限、有效期和独立执行账。框架 interrupt 负责暂停与恢复，不代替这些业务校验。是否进一步采用通用 HITL 中间件需通过跨请求确认、重复回放与未知结果测试；本轮不另加第二个确认系统。

## 证据与限制

生产失败样本在继承四个管理领域后，先读通知，再因资源不足进入无工具收尾；没有准备用户已要求的确认卡，并被记录为普通答复。这证明旧目录优化损害了任务完成，不能靠提高缓存百分比验收。

同一合成历史、请求、模型和 30K 上限的隔离对照，继承方案约 22.2K token 未准备确认，任务内激活约 18.8K 到待确认，确认参数通过实际领域校验。均未批准业务操作；这是一次机制验证，不是任务成功率或线上全量成本结论。新回复没有完整展开用户要求的未读摘要，确认后导航也未在本样本中执行，不能把“到了确认卡”计为整项任务通过。一次工具发现调用的额外开销与跨任务 schema 变化需要继续按完整任务测量。

回归覆盖完成后新任务、历史压缩、同任务取消恢复、目录撤权、模型与工具上限、输入容量、结果容量、回执保留及实际阶段。全量真实回归仍需验证未读总结、确认后导航和长会话中的连续任务；当前决策不宣称这些已全部通过。
