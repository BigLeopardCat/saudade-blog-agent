# 反馈与离线改进

改进链路包括反馈复核、独立验收数据、候选生成、配对比较和发布审核。模型可以辅助提出候选，不能自行修改线上提示、权限或发布门禁。

## 数据

- trace 关联请求、构建、角色、任务、工具结果、模型 usage 和用户反馈。
- 反馈先标为待复核；确认成功、功能缺陷、表达缺陷和证据不足应分别记录。
- 训练/开发集与独立验收集分离，同一事件的改写或多轮不能跨集泄漏。
- 删除或降权用例需要业务依据；视觉不支持项单列，不能为提高成绩移除失败场景。
- 生产派生材料外发 judge 前脱敏并取得相应授权；线上凭据和确认令牌不参与评审。

## 候选与验收

候选绑定基线提交、模型、配置、数据集哈希和改动范围。先做无网络行为回归，再跑少量真实请求，最后用相同输入进行配对对照。

确定性断言先检查授权、目标、写入和恢复事实。LLM judge 检查语义完成度、幻觉与业务规则，并通过人工标注样本校准误报/漏报。judge 不能覆盖硬失败，也不能批准业务写入。

比较需同时展示成功率、失败明细、置信区间、调用次数、全部费用、首事件/首正文与端到端延迟。非劣效结论应事先约定容差；样本不足标为未验证，不能用单个好案例替代。

通过[发布验收](release-acceptance.md)后，由维护者发布固定版本。灰度异常可回滚代码，业务数据按独立恢复策略处理。保留原始评测报告，不把部署成功等同于质量通过。

执行入口以 `eval/` CLI 的 `--help` 和[评测说明](eval-observability.md)为准，评价规则由版本化配置管理。
