# 故障排查

记录时间、请求 ID、现象和实际版本，再区分浏览器、宿主、Agent、供应商与业务事务。
模型回复、开发 HEAD 和健康状态都不能单独代替执行证据。

## 版本与就绪

在受控服务器对实际服务做只读检查，自定义端口及服务名使用真实配置：

```sh
curl --fail http://127.0.0.1:8010/version
curl --fail http://127.0.0.1:8010/health
curl --fail http://127.0.0.1:8010/ready
systemctl show saudade-agent -p User -p WorkingDirectory -p EnvironmentFiles -p ExecStart
journalctl -u saudade-agent --since '15 minutes ago' --no-pager -n 100
```

不要输出整个进程环境或环境文件。version 标识进程加载的构建；widget pin 只控制静态组件。
ready 不调用模型，也不证明 checkpoint、外部 API 和业务事务均已验证。

## 定位一次请求

1. 从宿主请求或服务日志取得 trace ID 和时间，核对实际构建。
2. 查看实际 `TRACE_DIR`；相对路径取决于工作目录，生产与开发不共用状态目录。
3. trace 通常按日期子目录保存；用明确目录与时间缩小范围，不扫描整台服务器。
4. 核对身份来源、模型事件、工具结果、任务状态与完成原因。只分享脱敏片段。

日期使用运行进程本地时区，可能与浏览器不同。退出或落盘失败时，部分阶段仍在服务日志；
没有最终 JSON 不证明请求未执行。[trace 实现](../utils/trace.py)与
[观测口径](eval-observability.md)解释展示截断和缺失字段。

| 核对事实 | 优先证据 |
| --- | --- |
| 模型调用、重试与用量 | llm_start/done/error、原始 usage、任务预算及结束原因 |
| 工具实际结果 | 调用及结果状态，不只看进度文案 |
| 全文总结 | document_summary 的源版本、覆盖和完成状态；仍须检查内容忠实度 |
| 写入完成 | 有效业务回执或真实状态查询；未知不能补为成功 |
| 补充是否应用 | task_input 状态，接收不等于采用 |
| 材料是否进入上下文 | 工具证据和请求布局；trace 截断不等于模型输入截断 |

## 按现象处理

| 现象 | 优先核对 |
| --- | --- |
| ready 503 | reasons、运行时构造、供应商及两个必要签名密钥；修改正确配置后重启 |
| 登录正常但工具 401/403 | 当前角色、冻结状态、断言签名及委托期限 |
| 暂停或确认不可用 | checkpoint、角色与条件能力；ready 不能证明恢复能力完整 |
| 旧卡过期或目标冲突 | 重新读取、准备并审阅，不修改旧令牌或覆盖目标版本 |
| 写入超时或断流 | 先查原操作与真实状态；公告可查同编号回执，不换编号盲重试 |
| 没收到 SSE done | 连接、Agent 错误和宿主保存分别核对；可能已有业务副作用 |
| 会话忙碌或迟到更新 | 会话锁、在途轮次及前端身份绑定，不清执行账解锁 |
| 模型 429/5xx 或无正文 | 供应商配额、限流、状态和结束原因，重试仍受任务预算约束 |
| 检索退回词法或不可用 | 公开性、源版本、embedding 空间、认证及向量完整性；[RAG](rag-design.md) |
| 后台未执行或未回报 | Worker、有限委托、当前权限、触发时区与来源会话结果分别核对 |
| 图片预览或裁剪失败 | 在宿主核对图片来源、签名期限、CORS 与实际响应 |

## 定位 RAG 和正文问题

用问题原话、预期来源和同次请求的 trace 定位最早出错的一步。已知文章编号时，先确认选的是直接读文章、全文总结，还是篇内检索，不要求每次出现全站检索事件。

| 现象 | 核对依据 |
| --- | --- |
| 没找到文章或找错文章 | 确认宿主公开语料有目标文章及当前修订。区分标题关键词候选和 RAG 正文候选。若走 RAG，查看 `rag.retrieval` 的模式、降级原因和向量缺失计数；查索引口径见[检索设计](rag-design.md)。 |
| 文章正确，命中段落不对或范围不足 | 看 `article_observation`、`article_evidence` 中的文章、版本与实际覆盖。把定位结果与同版本原文对照。全文任务另核对 `document_summary` 的覆盖与交付状态。 |
| 读到了正确证据，答案仍有误 | 对照模型实际看到的工具材料与答复，检查是否遗漏来源、混淆文章或加入材料外结论。固定同一问题和语料做复核，把缺陷归到读后组织或生成。 |
| 启用向量后仍退回词法 | 核对 embedding 认证、profile 与向量维度，检查 `/health` 的 `rag_state`、`vector_missing` 和 trace 的降级原因。可用性及重建步骤见[向量部署](deployment.md#向量存储)。 |

## 清理与恢复

会话、确认、执行账和后台去重记录不是可随意清掉的缓存。取消不回滚业务效果；
历史回执也不代表资源现在仍存在。未知结果按[写入契约](identity-and-permissions.md)核对；
还原和回滚走[部署](deployment.md)，后台保留策略见[调度](scheduling.md)。

上报问题保留脱敏构建号、时间、请求 ID、结果状态及复现步骤。真实私信、原始 trace、
确认凭据和配置不进 GitHub；安全问题按 [SECURITY](../SECURITY.md)处理。
